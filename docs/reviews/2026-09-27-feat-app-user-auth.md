## Major
### 🟠 Sign in and self service password checks hash attacker controlled input of unbounded size, `server/src/Orvano.Auth/Application/AccountService.cs:131`
**Problem**: `SignInAsync` and `CheckPasswordAsync` (used by `UpdatePasswordAsync` and `DeleteAsync`) intentionally still run one Argon2id hash when the password fails `PasswordPolicy.TryNormalize`, so an unknown email or a wrong password cost the same one hash (AC-4's enumeration protection). But when the password fails normalization only because it is too long (`PasswordPolicy.TryNormalize` rejects anything over `MaxLength * 4` = 1024 UTF-16 code units, and the sign up path rejects it before ever hashing), the sign in and self service paths do the opposite: they pass the raw, un-truncated `password` straight into `hasher.TryVerifyAsync` (line 131) or `hash` check (line 280), which UTF8 encodes it and feeds it to the Argon2id KDF. There is no request body size limit configured anywhere in the server (`grep`-ed for `MaxRequestBodySize`/`RequestSizeLimit`, found none), so Kestrel's default 30 MB cap is the only ceiling. `POST /v1/account/sessions/password` needs no credential and only a project header.
**Why it matters**: An attacker can send large JSON bodies (tens of MB of `password`) to the public, unauthenticated sign in endpoint (and the console's `consoleAccount.createSession`, which shares this code path). Each request UTF8-encodes and Argon2id-hashes that string, on top of the per-process budget the design explicitly sized for the container: the spec calls out "at most 4 hashes at once... about 76 MB of the 384 MB container", and the concurrency semaphore only bounds Argon2id's own working set, not the size of the string handed to it or the memory the JSON body occupies while being parsed and held live for the length of the hash. A handful of concurrent large-body requests can push memory well past what the design assumed, and the built in `SignInPerIp` limit (300 per 15 minutes) does not stop a single request from being large, nor does it stop an attacker using several source IPs. This undermines the explicit resource budgeting the rest of `PasswordHasher` and `AuthTimings` was designed around.
**Suggested fix**: When the password fails `PasswordPolicy.TryNormalize` for any reason (not just when the email is unknown), hash a small fixed size stand in (or truncate to `PasswordPolicy.MaxLength` code points) instead of the raw value, the same way an unknown email already falls back to the dummy hash. This keeps the "exactly one Argon2id run either way" property for timing safety while bounding the size of what actually reaches the KDF. Consider also capping the request body size on these routes as defense in depth.

## Minor
### 🟡 Spec 0004's route table has drifted from the shipped console route shape, `docs/specs/0004-app-user-auth/index.md:259-261`
**Problem**: Spec 0004's API surface section documents `consoleUsers.*` and `consoleAuthKeys.*` under `/console/projects/{projectId}/users/...` and `/console/projects/{projectId}/auth/keys/rotate` (a path parameter). The shipped contract (`contract/auth/console-users.tsp:46,69`) and the implementation (`server/src/Orvano.Auth/Endpoints/ConsoleUsersEndpoints.cs`, whose `RequireRole` filter reads only `X-Orvano-Project` from the header, never a route value) instead use `/console/project/users/...` and `/console/project/auth/keys/rotate`, taking the project from the header exactly as `contract/AGENTS.md` documents ("Project scoped console operations take the project from X-Orvano-Project (never a path parameter)").
**Why it matters**: The implementation, the contract, and `contract/AGENTS.md` all agree with each other, so this is not a functional bug, but spec 0004's own route table is now wrong and would mislead anyone reading it as the source of truth for the wire shape, or anyone using it to write a new console endpoint by copying the pattern shown there.
**Suggested fix**: Update spec 0004's API surface table (and rationale, if it says more) to show `/console/project/...` with no path parameter, matching what was actually built and what `contract/AGENTS.md` already documents as the convention.

## Nits
- ⚪ `server/src/Orvano.Auth/Application/Sessions.cs:22`, `ClientInfo.Cut` truncates `userAgent`/`sdk` by UTF-16 code unit count (`value[..max]`), which can split a surrogate pair at the 512/100 boundary and leave a lone surrogate in a `text` column value. Very unlikely to matter in practice for a `User-Agent` or SDK header, but truncating on a rune boundary would be strictly safer.

## Strengths
- The refresh decision table (rotate, replay within grace, reuse after grace, refuse) in `server/src/Orvano.Auth/Domain/Sessions.cs` and `Application/SessionService.cs` matches spec 0004 exactly, including locking the session row `FOR UPDATE`, and is proven under real concurrency by `SessionTests.cs` (two parallel refreshes of one token, reuse after 11 seconds ending the session and evicting the cache at once, a made up secret changing nothing).
- `SecretBox`/`MasterKeys` envelope encryption and `PasswordHasher`'s constant-Argon2id-run enumeration defense (dummy hash for unknown emails, malformed-hash still spends one run) are implemented carefully and match the spec's constant time intent; `DataHandlingTests.cs` proves after a full account lifecycle that no event payload, problem body, or log line carries an email, password, token, hash, or client IP/UA.
- JWKS caching, algorithm pinning (ES256 only), and clock leeway are implemented identically across the server, `@orvano/js`, the .NET SDK, and `orvano_dart`, down to the "refetch on unknown kid at most once per 30 seconds with Cache-Control: no-cache" detail (AC-19).
- The console CSRF rule (`ConsoleSessions.cs`) correctly treats a present but non-`same-origin` `Sec-Fetch-Site` value as a rejection rather than falling back to `Origin`, and `ConsoleAccountTests.cs` exercises `cross-site`, missing metadata with a foreign `Origin`, and the valid case together.
- The Next.js route handler's origin check (`request.headers.get('origin') !== request.nextUrl.origin`) runs before any cookie is read, exactly matching AC-23, and correctly rejects a missing `Origin` header (`null !== string` is always true).
