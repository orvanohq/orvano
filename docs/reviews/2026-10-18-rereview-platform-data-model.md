## Minor

### 🟡 Owner stamping is tested for one of its four paths, `server/tests/Orvano.SharedKernel.Tests/Data/PostgresConventionTests.cs:276` and `server/src/Orvano.SharedKernel/Data/TimestampInterceptor.cs:69`

**Problem**: The first review's fix says an owned item that is added, changed, or deleted stamps its owner, found upward through ownership keys, including nested owners. Only the changed value case has a test. Setting `Label` from null to a value (owned Added), setting it back to null (owned Deleted, which reads `OriginalValue` of the key), a nested owned chain, and an `OwnsMany` item are never run.
**Why it matters**: The deleted and nested branches are the fiddly part (original versus current key values, a loop up the ownership chain). They are the ones most likely to be wrong, and nothing would notice.
**Suggested fix**: Add three short tests on the existing `Widget.Label`: null to value, value to null, and one more owned level (or an `OwnsMany` on `Gadget`), each asserting `UpdatedAt` moved.
**Resolution (fixed, /debug 2026-10-18)**: The sample `Widget` now has a nested owned `Label.Note` and an owned collection `Tags` (`WidgetTag : Entity`, keyed on `Id`). Four new tests in `PostgresConventionTests.cs`: owned value added, owned value removed, owned value two levels down changed, and an owned collection item added then removed; each asserts `UpdatedAt` moved. Mutation checks: walking only one ownership level fails the nested test; stamping only `Modified` owned entries fails the added, removed, and collection tests. Honest limit: reading `CurrentValue` instead of `OriginalValue` for a deleted owned entry still passes, because EF keeps the key and ownership values on a deleted owned entry. That branch stays as a guard, but no test can tell it apart today.

### 🟡 The key rule now flags every `OwnsMany`, `server/tests/Orvano.ArchitectureTests/Data/DataModelRules.cs:172`

**Problem**: Including owned types in `Keys` is right, but an owned collection gets a shadow `int Id` that EF generates in the database. That fails the rule as "a key generated by the database (IDS-1)". Reasoned from EF's conventions, I did not run it. No sample or test covers an owned collection, and nothing says what a module should do.
**Why it matters**: The first module that uses `OwnsMany` gets a failing architecture test with no documented way out. Either the rule is right (then say that owned collections need an app made key) or it should skip owned collections.
**Suggested fix**: Decide, then add a sample context for it and one sentence in the rule's doc comment or in spec 0011 AC-8.
**Resolution (fixed, /debug 2026-10-18)**: Decided the rule is right. An owned collection is a table of its own, so it keeps IDS-1 ("no table has a database default for its id"). The way out: derive the item from `Entity` and key it with `HasKey(x => x.Id)`; the convention already sets `ValueGeneratedNever` on `Entity` keys. The rule's doc comment says this, and its message for an owned collection's shadow key now names the fix. New sample `OwnedCollectionContext` (one default `OwnsMany`, one keyed on `Id`) and test `Keys_fails_for_an_owned_collection_on_the_default_key_and_passes_one_keyed_on_Id`. The SharedKernel sample `WidgetTag` shows it working against PostgreSQL. Spec drift: AC-8 and IDS-1 should say this (see the note at the end).

### 🟡 `HasTextEnum` can still end up with no CHECK in two cases, `server/src/Orvano.SharedKernel/Data/OrvanoConventionSetPlugin.cs:90`

**Problem**: The annotation is removed first, then `if (table is null) continue;`. A property on an entity with no table gets no CHECK, and the new "leftover annotation" rule cannot see it because the annotation is already gone. Separately, `HasTextEnum` on a property inside a complex type is never visited (only `entityType.GetDeclaredProperties()` is), so no CHECK is made; the rule does flag it, but with the message "no CHECK" rather than "not supported here".
**Why it matters**: Low odds today (no such entity exists), but this is the same quiet failure class the first review was about.
**Suggested fix**: Throw at model finalize when a `HasTextEnum` property has no table, and walk complex properties (or throw with a clear message that complex types are not supported).
**Resolution (fixed, /debug 2026-10-18)**: `OrvanoConventionSetPlugin.AddTextEnumChecks` now throws when a marked property's entity has no table (the mark is no longer removed before the check), and walks complex properties, nested too, throwing "HasTextEnum is not supported inside a complex type" for a marked one. Tests `Model_build_throws_when_a_text_enum_has_no_table_for_its_CHECK` (`ToView`) and `Model_build_throws_when_a_text_enum_is_inside_a_complex_type` in `ConventionModelTests.cs`.

### 🟡 The deferred "minimum production contexts" check is written down only in the first review, `docs/reviews/2026-10-18-review-platform-data-model.md:55`

## Nits

- ⚪ **Fixed.** `server/src/Orvano.SharedKernel/Data/TimestampInterceptor.cs:71`, every save copies all tracked entries into a list and, for each changed owned entry, scans that list (owned changes times tracked entries). A bulk save of 10k entities with owned types is quadratic. Skip the walk when the model has no owned types, or index the entries by entity type. _Resolution_: both. The walk returns at once when no owned entry changed, and owners are found through a dictionary keyed on (key, values), so the save stays linear.
- ⚪ **Fixed.** `server/src/Orvano.SharedKernel/Data/OrvanoConventions.cs:47`, `ReplaceService<IModelCacheKeyFactory, ...>` means a module cannot use its own cache key factory. Say so in the XML doc of `UseOrvanoConventions`. _Resolution_: the XML doc now says it.
- ⚪ **Fixed.** `server/tests/Orvano.SharedKernel.Tests/Data/PostgresConventionTests.cs:295`, the test name says "a delete saves" but only the unchanged half checks timestamps; the name could say "a delete removes the row". _Resolution_: renamed to `Updated_at_stays_when_nothing_changed_and_a_delete_removes_the_row`.

## Strengths

- Each fix comes with a test that really fails on the old behavior (the unmarked value object sample, the AutoDetect off save, the owned value change, the base64 assertion), not a test that restates the fix.
- `SchemaOf` plus the `Setup` rule is a small public surface that makes the "forgot the call" mistake loud, and the bad sample contexts prove each of its four messages.
- Making the extension hash constant and reading schema and clock per context is a clean way to avoid one EF service provider per clock; the cache key factory covers the one place that did depend on the schema.
- The migration test with two modules on one database is the right shape for the history table rule.
