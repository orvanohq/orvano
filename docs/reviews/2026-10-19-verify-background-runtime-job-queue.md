## Spec corrections for /architect

1. **CLM-1 claim SQL does not run as written.** On PostgreSQL 18.6 the spec's statement (each `UNION ALL` branch in
   parentheses with its own `FOR UPDATE SKIP LOCKED`) fails with `ERROR: FOR UPDATE is not allowed with
   UNION/INTERSECT/EXCEPT` (`0A000`). I ran it verbatim in `psql` and saw that error. The built `ClaimSql`
   (`server/src/Orvano.Infrastructure/Jobs/JobExecutor.cs:47`) wraps each branch in its own derived table
   (`SELECT id FROM (… FOR UPDATE SKIP LOCKED) AS due UNION ALL SELECT id FROM (…) AS expired`), keeping the same
   predicates, the same `ORDER BY` and `LIMIT @free` per branch, the outer `LIMIT @free`, and the same `SET` and
   `RETURNING`. I checked it is equivalent on the live schema, inside a rolled back transaction with 10,000 future
   `queued` rows, three due rows (d1 to d3, `run_at` out of id order), two expired `running` rows with attempts left
   (e1, e2), and one expired on its last attempt (e3):

   | Call                     | Rows claimed, in order              | What it shows                                                                                           |
   | ------------------------ | ----------------------------------- | ------------------------------------------------------------------------------------------------------- |
   | `@free` 4, d1 in `@mine` | d2, d3, then e2, e1                 | due by `run_at, id` first, then expired by `locked_until, id`; `@mine` and the last attempt row skipped |
   | `@free` 2                | d2, d3; e1 and e2 still `running` 1 | expired rows only while slots remain                                                                    |
   | `@free` 1, d2 in `@mine` | d3                                  | the running set is honored                                                                              |

   Leases came out per kind: 1 minute for kinds passed in `@kinds`, 5 minutes for a kind left out. `EXPLAIN (ANALYZE)`
   shows `Limit → Append` over two `LockRows → Index Scan` nodes, on `ix_job_due` (index condition `run_at <= @now`,
   2 rows) and `ix_job_lease` (`locked_until < @now`, 2 rows), 20 buffer hits in all, so the 10,000 future rows are
   never read. One small bonus: when the due branch fills the outer limit, the `Append` never runs the expired branch,
   so it locks nothing (the spec's note about a dropped row staying as it was still holds). Suggested spec change: show
   the derived table form in CLM-1, with a one line reason.

2. **OUT-3 and the value sourcing table name `Random.Shared`.** `System.Random` is banned repo wide
   (`BannedSymbols.txt`, TOK-1), so `JobBackoff.NextRandom()` uses `RandomNumberGenerator.GetInt32(int.MaxValue) /
   (double)int.MaxValue`. That is uniform over [0, 1 − 2^−31], the same range the spec asks for, and `Delay` clamps
   its input to [0, 1] anyway. The cost (one CSPRNG call per failed attempt) does not matter at retry rates. Observed
   retries landed inside the bounds (below). Suggested spec change: name `RandomNumberGenerator` in OUT-3 and the
   _Retry, delay_ row.

## How the probes ran

A small startup hook (`DOTNET_STARTUP_HOOKS`, in the session scratchpad outside the repo and deleted with it) loaded
into the real `orvano serve` process, built from this commit's `Orvano.Host` output. It registered three probe kinds
(`probe.run` with lease 1 minute and 3 attempts, `probe.slow` with a 2 s timeout and a handler that ignores its token,
`probe.project` with `RequiresProject`), an optional `probe.every` schedule, and a few `AllowPublicAccess` GET routes
that call `IJobQueue` in and out of an `InTransactionAsync` on `JobsDbContext`. Each handler wrote a row to a
`probe.ran` table (job id, attempt, process id, caller, project) so timing and "exactly once" came from SQL. Host A ran
role `api`; hosts B and C ran `worker`. A `psql` `LISTEN orvano_signal` tap timestamped every notification. Rows that
needed a hand made state (unknown kind, bad payload, expired leases, old finished rows) were inserted with `psql`. The
listener outage used a PostgreSQL 18 login event trigger that refused only B's `orvano-signals-<id>` application name.
Bad registrations used the existing `Orvano.Testing` hook (`TESTHOOK_JOBS`). Every process and the container were
stopped afterwards.

Side effect worth knowing when reading the AC-21 row: the short hookless worker runs I used for the AC-26 defaults
claimed some due probe retries and, correctly, failed them as `no handler registered for kind` until they died at 3
of 3. That is OUT-2 behaving as specced, not a fault.

## For /check review and later

- A bad registration prints a clean stderr line and exits 1, but the generic host also writes an Error JSON log line
  `Hosting failed to start` with the full stack trace on stdout. This is how every `StartupFailedException` behaves
  since earlier features, not new here; worth a look if operators should never see a stack.
- `jobs` is now the first migrated context, so on a fresh database `orvano migrate` logs an EF Error (`Failed
  executing DbCommand … FROM jobs.__ef_migrations_history`) before it creates the history table. Harmless, but a first
  install now shows an Error line.
- The "attempt failed" Warning formats the next run time with the current culture (`10/20/2026 06:45:53 +00:00`). A
  round trip format would read better in JSON logs.
- When a timed out handler finally returns, its freed slot waits for the next poll unless the last claim was full
  (WAK-2 (4)). That is as specced; with a long `PollInterval` a freed slot can sit idle up to one poll.
- `ORVANO_JOBS__CONCURRENCY` above half the pool also stops an `api` only process, which never runs the runner. The
  spec does not limit the check to the worker role, so this is consistent, just stricter than needed.
- Two follow ups from the develop notes for `/sync`: document `ORVANO_JOBS__POLLINTERVAL`, `ORVANO_JOBS__CONCURRENCY`,
  the one connection per handler rule (JOP-4), `JobsDriver`, and `CreateMigratedDatabaseAsync` in `server/AGENTS.md`.
