# Review, background runtime job queue (milestone 2), 2026-10-20

**Note on scope and status**: the feature 61 `Review it` box in `docs/scope/foundations.md` stays unticked, because milestone 3 (the outbox) is still unbuilt and the feature is not complete until it is reviewed too. The outbox's absence is not a finding. The two spec corrections already owed to /architect (the CLM-1 derived table SQL shape and the OUT-3 `RandomNumberGenerator` jitter source) are not repeated here.

**Reviewed by**: Claude Sonnet 5.5 (fresh review; the author's model is not recorded in the commits)
**Scope**: 67 files, range `0e27e1d..51e4659` (PR #54 `c17cff3` built it, PR #55 `51e4659` tested it). Already merged, so this is a range review and not a branch diff.
**Verdict**: Changes requested

## Summary

The change adds the job queue, the runner, the executor with its claim, lease, renewal and outcome logic, the scheduler, the cleanup job, the `jobs` schema, and the tests around them. The core design is careful. The fence is `(id, status, locked_by, attempt)` and it holds up under every race I traced, renewals are awaited before the outcome is written, time goes through the injected `TimeProvider`, and the SQL is parameterized throughout. I found one Major bug: an exception thrown before the handler starts leaks the job's slot forever, and a legal option value (`Timeout` over about 49.7 days) throws exactly there. I found a second Major: the claim runs with no deadline, which is the AC-8 bug class again. The rest are Minor and Nit items, including the outcome write failure reporting you asked about, which I judge a real (small) defect.

## Weighed points, one verdict each

1. **Claim and fence correctness under races: no hole found.** `ClaimSql` (`JobExecutor.cs:47`) picks rows with `FOR UPDATE SKIP LOCKED` inside derived tables, then updates by id in the same statement, so two workers cannot take one row. Every later write carries the fence at `JobExecutor.cs:251`. A different worker always has a different `locked_by`, because `OrvanoInstance` makes a fresh id per process start (`OrvanoInstance.cs:20`), so the ABA case (release lowers `attempt`, a later claim raises it back to the same number) cannot match a stale writer: the `locked_by` differs. The same worker cannot re-claim its own row while its handler runs, because `@mine` excludes it (`JobExecutor.cs:56`, `:60`, `:149`). The release statement's `attempt = attempt - 1` (`JobExecutor.cs:360`) cannot go below 0 because a claimed row has `attempt >= 1`, and `ck_job_attempt` backs that up (`JobsDbContext.cs:28`). The one honest cost is CLM-3, an accepted spec price. A retried outcome write whose first try already committed finds no row and reports a lost lease, which OUT-7 says is harmless.
2. **Renewal timers and cancellation: no hole found.** The order at `JobExecutor.cs:490-499` is right: set `_handlerReturned`, dispose the timer (which waits for a callback in flight), read `_renewal` under the lock, await it, and only then write the outcome. No renewal can start after the timer is disposed, and `OnRenewTick` returns early once `_handlerReturned` is true (`:619`). A renewal that finds the row gone after the handler returned does not cancel anything (`:662`), so the later fenced write reports the lost lease cleanly. Two small robustness points are findings 7 and 8 below.
3. **Awaits with no deadline (the AC-8 class): one real repeat, finding 2.** The claim uses `CancellationToken.None` (`JobRunner.cs:135`). The rest, checked one by one: outcome and release writes are bounded by `WriteBound` 10 s (`JobExecutor.cs:386`); renewals by lease divided by 3 (`:649`) plus a command timeout; the wake wait, the poll and the signal handler are cancelled by the stopping token or never block (`WorkerWake.cs:64`, `:92`); the schedule sync and tick take the stopping token, so they stop at shutdown but have no deadline of their own while the host runs. `Task.WhenAll(_attempts.Keys)` at `JobRunner.cs:86` has no deadline except the host's 25 s, which is by design (OUT-6). The rollback after a cancelled write uses `CancellationToken.None` (`OrvanoTransactions.cs`), and disposing the scope happens outside the 10 s token. Both lean on Npgsql's 30 s command timeout. I could not confirm a hang here and did not raise it.
4. **Shutdown and release ordering against 25 s: sound, with caveats.** The order is correct: the loop stops, the claim in flight finishes, then handlers are cancelled, then each is released or writes its outcome (`JobRunner.cs:80-91`). `ServeCommand` sets `ShutdownTimeout` to 25 s and `deploy/compose.yaml:59` sets `stop_grace_period: 35s`, which is a 10 s margin. The other `deploy/compose.yaml` services run no `serve`, so none needs it. Caveats: the 25 s is shared with every other hosted service, and (unconfirmed, from how the generic host orders its stops) the web server stops before the runner, so the runner gets what is left after the HTTP drain. A renewal in flight is awaited before the release write (`JobExecutor.cs:499`) and can take up to lease divided by 3 (at least 20 s) when the database is slow, so under a degraded database a release can miss the 25 s. The consequence is only lease recovery (CLM-6). This links to finding 2.
5. **Exactly once schedule firing across workers: no hole found.** `DueSql` locks with `FOR UPDATE SKIP LOCKED` (`JobScheduler.cs:39`), the enqueue and the `next_run_at` move share one transaction (`:96-147`), and the dedupe key `<name>:<fire time>` is unique (`ux_job_dedupe_key`), so even a retried unknown commit cannot fire twice. Test `Two_workers_ticking_at_the_same_instant_...` covers it. Side issues are findings 4 and 5.
6. **`CancelProjectJobsAsync` versus a running handler: works as specified, one thing to know.** The update marks queued and running rows dead and clears the lease (`JobQueue.cs:59-62`). The handler loses its lease at its next renewal tick, so it can keep running for up to lease divided by 3 (20 minutes for a 1 hour lease) after the project is deleted. Its later outcome write is fenced out and reported as lease lost (test at `JobRunnerTests.cs:387`). The interface comment already tells callers that handlers must refuse a deleted project, so I did not raise a finding. The cancelled rows are not counted in `jobs.attempts`, which is a gap in metrics but not a defect.
7. **Connection and pool use (JOP-4): acceptable, see finding 6.** Every draw comes from the one platform pool: the claim, the schedule sync and tick, each handler, each renewal (`RenewalOptions` uses the same `NpgsqlDataSource`, `OrvanoConventions.cs:40`), and each outcome write. The renewal and the outcome write of one attempt never overlap because the renewal is awaited first, so the worst case is about 2 times Concurrency plus 1, not more.
8. **`last_error` content: no hole beyond what OUT-5 accepted.** `LastError` keeps only the exception type and top level message, cut to 2000 characters (`JobExecutor.cs:261`), and the column is marked `DataClass.Personal` with an honest comment (`Job.cs:37`). In production `IncludeErrorDetail` is off (`PlatformDatabase.cs:63`), so PostgreSQL row values are not in the message. The refusal text `payload could not be read: <JsonException message>` carries a path and position, not values. What can still leak is a handler's own exception message (for example a `FormatException` that quotes its input). That is the documented price. Whatever shows `last_error` later (feature 46) must treat it as Personal. The Error level `JobDead` log repeats the same reason text, and the payload and dedupe key appear only at Debug (`InfrastructureLog.cs`, `JobEnqueued`), as JTL-2 says.
9. **Caller.System and project scoping (AC-23): correct.** `JobAccessScope.Establish` runs first in a fresh scope per attempt (`JobExecutor.cs:568-569`), `Caller.System` is the caller and the project is set only when the row has one. Note `Caller.System.BypassesGrants` is true (`Caller.cs:72`), so the access layer does not confine a project job to its project. The handler must scope its own work by `IProjectContext`. That is spec 0012 behavior, not a defect, but it is worth a line in the handler guidance.
10. **Can modules bypass `JobAccessScope`: no.** `AccessContext.Establish` is `internal` (`AccessContext.cs:49`), the type ban is in `BannedSymbols.Modules.txt`, the IL scan test `Only_the_access_layer_and_JobAccessScope_set_the_caller_and_project_when_built` fails if any other type calls `Establish`, and the module source scan rejects `jobs.job` and `jobs.schedule`. See Nit 5 for the one thing that scan does not cover.
11. **All time through the injected `TimeProvider`: clean.** I grepped `Orvano.Infrastructure/Jobs`, `SharedKernel/Jobs` and `Host/Database` for `DateTime(Offset).UtcNow`, `Stopwatch`, `Task.Delay`, `Random.Shared`, `now()`, `clock_timestamp`, `CURRENT_TIMESTAMP`. The only timer API is `PeriodicTimer(..., _time)` (`JobRunner.cs:109`). Timers, timeouts, elapsed time and every SQL time come from `_time`. `JobTimeTests` enforces the SQL half. The inconsistency risk between the application clock and PostgreSQL `now()` does not exist here. (Cross host clock skew is the accepted CLM-8.)
12. **Metric and log hygiene: good.** Tags are `kind`, `outcome` and `schedule`, all from code. The job id and attempt appear only as activity tags, as JTL-3 allows. Log event ids `+100` to `+119` are unique and inside the reserved range. Payloads are logged at Debug only. Nit 4 covers the one tag that is read from the database.
13. **Outcome write failure reported as the intended outcome: a defect, Minor, see finding 3.**

## Major

### 🟠 1. An exception before the handler starts leaks the slot for good, and a `Timeout` over about 49.7 days triggers it, `server/src/Orvano.Infrastructure/Jobs/JobExecutor.cs:459`

**Problem**: `Attempt.RunAsync` builds `new CancellationTokenSource(_registration.Options.Timeout, time)` at `:459`, before any `try`. That constructor throws `ArgumentOutOfRangeException` for a delay above about 49.7 days (4,294,967,294 ms). I ran it: 40 days is fine, 50 days and `TimeSpan.MaxValue` both throw. `JobKindOptions.Timeout` has no upper bound (`JobRegistration.cs:196` only checks the 1 second minimum), so `Timeout = TimeSpan.MaxValue`, a natural way to say "no limit", is accepted at startup. On every attempt of that kind the exception escapes `JobExecutor.RunAsync` (the slot is freed only at `:239`, `:511` and `:612`, none of which is reached), and `JobRunner.RunAsync` catches it and only logs it as `JobOutcomeWriteFailed` (`JobRunner.cs:168-171`, a misleading message). The same leak happens for any other exception thrown before the outcome `try`, for example a `registration.Deserialize` that throws something other than `JsonException` (`JobExecutor.cs:220` catches only `JsonException`).
**Why it matters**: the job id stays in `_running` for the life of the process. Capacity drops by one slot per attempt, and because `@mine` excludes it (`:56`, `:60`), this worker never re-claims that job even after its lease expires. After `Concurrency` such attempts the worker claims nothing and logs nothing useful, until a restart. Other workers hit the same wall one by one. The row sits `running` until the lease expires, then another worker claims it, leaks again, and the job burns its attempts and ends `dead` with `lease expired on the last attempt`. The wrong, silent symptom makes this hard to diagnose.
**Suggested fix**: (a) validate an upper bound on `Timeout` in `EnsureValidOptions` (for example 24 hours, never above the CTS limit) and add a test for it; (b) make the slot release unconditional, for example wrap the whole of `JobExecutor.RunAsync` in a `try/finally` that frees the slot unless the abandoned handler path took it over, so no future early exception can leak; (c) in `JobRunner.RunAsync`, treat an exception that escapes the executor as a failed attempt (free the slot and write a fail outcome) rather than leaving the row to the lease.

### 🟠 2. The claim has no deadline, the same bug class as AC-8, `server/src/Orvano.Infrastructure/Jobs/JobRunner.cs:135`

**Problem**: `TryClaimAsync` calls `_executor.ClaimAsync(free, CancellationToken.None)` and the runner awaits it inline in the single loop (`JobRunner.cs:77`). The only bounds are Npgsql's defaults (30 s command timeout, 15 s connect and pool wait; the platform pool has no TCP keepalive, only the signals source does, `PlatformDatabase.cs:41`) multiplied by the EF execution strategy: `UseOrvanoConventions` calls `EnableRetryOnFailure()` with its defaults of 6 retries and up to 30 s between them (`OrvanoConventions.cs:44`), and `InTransactionAsync` runs under it (`OrvanoTransactions.cs:38`). Two claim transactions run per wake (`JobExecutor.cs:123`, `:150`). A silent connection or a stalled database can hold one claim for minutes. The schedule sync and tick are in the same loop; they at least get the stopping token.
**Why it matters**: two effects. While it runs, no job is claimed and no schedule fires on that worker. And at SIGTERM, OUT-6 says the claim in flight must finish before handlers are cancelled (`JobRunner.cs:80-84`); if the claim is stuck, the handlers are not cancelled or released within the host's 25 s, the host gives up and the process exits, and every running job waits out its full lease (up to an hour) instead of restarting at once. It needs a database fault to show, but that is when shutdown order matters most, and the prior review rated the same class (the signal dispatch loop) Major.
**Suggested fix**: give the claim its own deadline from a `CancellationTokenSource(bound, _time)` (spec 0002 ASY-7), a few seconds to about 10 s, with the execution strategy given that token, and let the loop log and wake again on a timeout. Accept that a cancelled claim may leave rows `running` with no task, which CLM-3 and CLM-6 already cover, and say so in OUT-6. Add a shutdown test that holds the claim on a locked row or a stalled connection and shows the handlers are still released.

## Minor

### 🟡 3. A failed outcome write is counted and returned as if it had succeeded, `server/src/Orvano.Infrastructure/Jobs/JobExecutor.cs:401-407`

**Problem**: when the write throws (OUT-7), the `catch` logs and falls through to `_telemetry.JobAttempted(job.Kind, outcome, duration)` and `return outcome`. The row stays `running`. So `jobs.attempts{outcome="succeeded"}` goes up for a job that will run again; when the lease expires and it succeeds a second time, it counts twice. `JobsDriver` and the runner get the intended outcome back: `JobRunner.cs:163` counts a `released` job and logs `Released N running jobs at shutdown` even when the release write failed (the job was not released), and the test `An_outcome_write_that_fails_is_logged_...` (`JobRunnerTests.cs:405`) does not assert the returned outcome, which would be `succeeded` with the row `running`. The same goes for a `dead` and a `failed` outcome, and for the activity status.
**Why it matters**: the only visible signal for a failing database write is then a log line. Dashboards show healthy success counts and also the extra attempts. A shutdown log claims jobs were released when they will actually wait out the lease.
**Suggested fix**: on the exception path, do not count the intended outcome. Either skip the metric and return a distinct value (for example `write_failed`, with a spec note adding it to the `outcome` tag set, since the tag values are spec bound) or count a separate failure counter. `JobRunner` must count `Released` only when the release was written. Extend the OUT-7 test to assert the returned outcome and the metric.

### 🟡 4. A schedule for a `RequiresProject` kind passes startup and then dies on every fire, `server/src/Orvano.Infrastructure/Jobs/JobRegistry.cs:95`

**Problem**: `Check` (SCH-1) rejects bad crons, missing handlers and oversized payloads, but not a schedule whose kind has `RequiresProject = true`. `JobScheduler.TickAsync` enqueues with no `ProjectId` and calls `InsertAsync` directly, skipping the `Check` in `JobQueue` that would refuse it (`JobQueue.cs:137`). The runner then kills the row with `project id missing` (`JobExecutor.cs:210-212`) each time. SCH-6 says schedules have no project.
**Why it matters**: a registration mistake becomes a silent, repeating dead job instead of a startup failure.
**Suggested fix**: add `registration.Options.RequiresProject` to the SCH-1 problems.

### 🟡 5. The dedupe key is global across kinds, so one module can silently suppress another's job, `server/src/Orvano.Infrastructure/Jobs/Data/JobsDbContext.cs:51`

**Problem**: `ux_job_dedupe_key` is unique on `dedupe_key` alone and `ON CONFLICT (dedupe_key) DO NOTHING` returns `null` on a hit (`JobQueue.cs:89-95`). Two kinds that both use a natural key such as `"project:<id>"` collide, and the second enqueue is dropped with only a `null` return. The scheduler's keys are `<name>:<time>` in the same space, so a stray equal key would suppress a schedule fire.
**Why it matters**: a dropped job is a lost side effect, found only if the caller checks the `null`. It is trusted code, so this is a contract trap, not an attack.
**Suggested fix**: make the stored key `kind + ':' + key` (or a unique index on `(kind, dedupe_key)`), and keep the doc comment honest about the scope either way.

### 🟡 6. The half pool rule counts handlers only, `server/src/Orvano.Host/Database/JobConcurrency.cs:20`

**Problem**: with `Concurrency` equal to half the pool and every handler holding a connection, each attempt's renewal or outcome write needs one more connection, plus one for the claim or tick. That is up to 2 times Concurrency plus 1, one more than the pool (default pool 30: 15 handlers, 15 renewals, 1 claim). JOP-4 states the assumption but nothing tests or logs it.
**Why it matters**: low probability (renewals take milliseconds and handlers hold a connection only while they use it), but when it happens request traffic waits on the pool and renewals can fail, which loses leases.
**Suggested fix**: either document that "half" is the typical case and the hard ceiling is the pool, or lower the default cap to leave room (for example pool divided by 2 minus 1), and add a test that holds every handler connection open while a renewal and a request both complete.

### 🟡 7. A handler's cancellation callbacks run on the renewal timer thread inside the lock, `server/src/Orvano.Infrastructure/Jobs/JobExecutor.cs:634`

**Problem**: `OnRenewTick` calls `LoseLease()` (so `_leaseLost.Cancel()`) while holding `_renewLock`, on a timer thread, with no `try/catch` (`:624-635`). `Cancel()` runs every registered callback synchronously, including a handler's own. A callback that throws makes `Cancel()` throw an `AggregateException` out of a timer callback, which is an unhandled exception and ends the process. A callback that blocks stalls the timer, and `renewTimer.DisposeAsync()` (`:492`) waits for it. The same holds, without the lock, for the timeout source.
**Why it matters**: needs a misbehaving handler or third party callback, so the odds are low, but the cost is the whole host.
**Suggested fix**: cancel with `CancelAsync()` and observe the returned task, or wrap `LoseLease()` in `try/catch` and log, and call it outside the lock.

## Nits

- ⚪ `server/src/Orvano.Infrastructure/Jobs/JobRunner.cs:181-189`, the catch filters `when (!stoppingToken.IsCancellationRequested)` and a second catch only for `OperationCanceledException`. A non cancellation exception thrown while the host is stopping (for example a connection error from the sync or tick) escapes `ExecuteAsync` and the host logs a critical `BackgroundService failed`. Log and swallow it instead. The same shape is at `:198-204`. At `:61` the first sync is outside the `try/finally` as well.
- ⚪ `server/src/Orvano.Host/Database/DatabaseOptions.cs:35`, `PoolSize` allows 1, and then the default `Concurrency` of 1 fails the half pool rule (`1 > 1 / 2`), so the "default can never fail startup" promise (JOP-2) breaks. Raise the minimum pool size to 2 or clamp the default.
- ⚪ `server/src/Orvano.Infrastructure/Jobs/JobExecutor.cs:200-231`, the `kind` metric tag is taken from the database row for an unregistered kind (`JobClaimed`, `JobAttempted`). It is bounded by what older versions wrote, so it is not a real cardinality risk, but a fixed `unknown` value for unregistered kinds would make the bound obvious.
- ⚪ `server/src/Orvano.SharedKernel/Jobs/JobAccessScope.cs:17`, the type is `public` and only banned for `Orvano.Modules.*`. The architecture test proves nobody but `JobAccessScope` calls `Establish`, but not that only the runner calls `JobAccessScope.Establish`. A test that scans the `Orvano.Host` and `Orvano.Infrastructure` call sites would close it.
- ⚪ `server/src/Orvano.Infrastructure/Jobs/JobExecutor.cs:123-147`, the dead marking is a separate transaction on every wake, even when nothing is expired. Cheap with `ix_job_lease`, but the two statements could share one round trip when a wake follows a busy queue.

## Strengths

- The fence is complete and uniform: one `Fence` constant (`JobExecutor.cs:251`) is used by renewal, success, failure, dead and release, so a fix to the rule changes all of them at once.
- The renew then outcome ordering, with the timer disposed before the in flight renewal is awaited, avoids the classic lost lease miscount, and the test `A_handler_that_returns_while_a_renewal_is_in_flight_...` pins it.
- Abandoning a timed out handler is done properly: the retry starts at once, the slot stays held, the id stays in `@mine`, and a reminder logs each lease period. The comment at `JobExecutor.cs:485` shows the author found and handled a real continuation race.
- Every time value is a parameter from one clock, enforced by a test that scans the SQL, and `ManualClock` makes the lease, backoff and poll tests exact instead of sleeping.
- Shutdown is thought through end to end: release restores the attempt, sends a `job` signal in the same transaction, uses its own 10 s bound, and a test shows a handler that ignores cancellation is left to its lease.
- Module isolation is enforced three ways (type ban, IL scan for `Establish`, source scan for the jobs tables), and the new `CalledMethods` helper is covered.
- The partial indexes match the claim and cancel queries, and the verify run checked the plan with 10,000 future rows.

## Test coverage

Strong overall: 763 tests pass, with real two host races (claim exactly once, schedule exactly once), lease recovery after a killed worker, shutdown release, outcome write failure through a trigger, project cancel versus a running handler, and the clock based renewal cases.

Gaps, tied to the findings:

- No test for a `Timeout` above the CTS limit, nor for any exception escaping before the handler runs, so the slot leak (finding 1) is unguarded.
- No test of a claim that hangs or fails during shutdown (finding 2). The existing shutdown tests use a healthy database.
- The OUT-7 test does not assert the returned outcome or the `jobs.attempts` count (finding 3).
- No test that a schedule on a `RequiresProject` kind is refused at startup (finding 4).
- No test for a cross kind dedupe collision (finding 5), nor for connection use while every handler holds one (finding 6).
- I could not confirm from the plan, only from the verify report's `EXPLAIN` at small sizes, that the `UPDATE ... FROM (subquery LIMIT ... FOR UPDATE SKIP LOCKED)` never claims more than `@free` rows when the planner picks a different join order with a large `@free`. The test `Two_workers_run_50_due_jobs_...` checks the per worker limit at 50 rows. A test at the maximum `Concurrency` of 256 over a large queue would settle it.
