## Summary

The change adds the module outbox (`IOutbox.Publish`, `OutboxEvent`, `HasOutbox`), the dispatcher (claim with `FOR UPDATE SKIP LOCKED`, one delivery job per subscriber, mark dispatched, all in one commit), the cleanup job, the PUB-3 before commit check, and the new pool rule (`PoolSize / 2 - 2`, minimum pool 6). I traced the dispatch transaction, the failure and rollback paths, the unknown commit outcome handling, the deadlines, the wake and shutdown ordering, and the dedupe scope. I found no blocker and no major. Every await in the dispatcher is bounded by `BatchBound` or the stopping token, the dedupe key holds under the per kind and project scope, and the tests are strong. The findings below are one real contract gap (the envelope size after `jsonb` text conversion) and several smaller points.

## Minor

### 🟡 `payload::text` can push a delivery over ENQ-3's 65,536 bytes, and nothing checks it, `server/src/Orvano.Infrastructure/Outbox/OutboxSql.cs:35`

**Problem**: PUB-2 caps the published JSON at 64,000 bytes "to leave room for the envelope under 65,536" (`Outbox.cs:28`). But the dispatcher does not read back what was published. It reads `payload::text` from a `jsonb` column (`OutboxEventConfiguration`, `OutboxEvent.cs`), and PostgreSQL prints `jsonb` as text with a space after every `:` and `,` (`{"a": 1, "b": 2}`). A compact payload made of many small members grows by about one byte per member. A 64,000 byte array of one digit numbers (`[1,2,3,...]`, 32,000 elements) comes back near 96,000 bytes, and the envelope (`OutboxDispatch.Envelope`, line 253, `WriteRawValue`) carries all of it. `JobQueue.InsertAsync` is called directly (`OutboxDispatch.cs:198`) and skips `Check`, which is where ENQ-3's size test lives (`JobQueue.cs`, `Check`), and `jobs.job.payload` is `jsonb` with no size constraint, so the insert succeeds.
**Why it matters**: The 65,536 limit is an invariant the spec states twice (PUB-2, DLV-2). Today the break is silent: oversized job rows are stored, claimed, and sent to workers, so the bound that protects the claim query and memory is gone. The unit test (`OutboxRegistrationTests.cs:210`) uses one long string member, which does not grow, so it cannot see this.
**Suggested fix**: Either measure the payload the way the dispatcher will read it (the publish side cannot see the `jsonb` text, so check the envelope length in the dispatcher before the insert), or have `Envelope` fail the row with a clear message and mark it dead for review rather than insert it, or raise the room under PUB-2's limit with a test that uses many small members. Add a test with a compact payload of many small members at the limit. If you pick the dispatcher check, make sure a row that fails it does not block its outbox (see the batch halving rules in DSP-5).

### 🟡 A short batch under two dispatchers ends the rounds early, and events with no subscriber then wait for a poll, `server/src/Orvano.Infrastructure/Outbox/OutboxDispatch.cs:93`

**Problem**: A round continues only for an outbox whose batch returned exactly `size` rows (`selected == size`). With `FOR UPDATE SKIP LOCKED` under read committed, a row that another dispatcher marks between this query's snapshot and its lock is dropped by PostgreSQL's recheck, so a batch can come back one row short of `LIMIT` while many rows still wait. The verify report lists this. What the report does not say is why it matters: the commit's `job` signal that normally wakes everyone for the rest (DSP-7) is sent only when a delivery job is inserted (`JobQueue.InsertAsync`, ENQ-4). A batch of events that have no subscriber (the normal case, DSP-4) inserts no job, so it sends no signal.
**Why it matters**: With several workers and a backlog of unsubscribed events, each pass can stop after one short batch and the rest waits for the next poll (5 seconds by default), so drain speed falls to about one batch per poll tick per worker. It is a latency problem, not a loss.
**Suggested fix**: You cannot tell a short batch caused by contention from a drained outbox, so the simplest rule is to continue the round while a batch selected any rows, and stop when one selects none. That costs one extra empty query per pass, which DSP-7 already accepts. Update DSP-2 to match.

### 🟡 A failure before the COMMIT statement still runs the after commit actions, `server/src/Orvano.SharedKernel/Data/SignalTransactionInterceptor.cs:68`

**Problem**: `RunBeforeCommit()` and the `pg_notify` commands run inside `TransactionCommittingAsync`. As I read EF's `RelationalTransaction.CommitAsync`, that call sits inside the same try block as the `COMMIT` itself, so a throw from it reaches `TransactionFailedAsync` with `Action == "Commit"`, which runs the after commit actions (`SignalTransactionInterceptor.cs`, `TransactionFailedAsync`) as if the outcome were unknown. For PUB-3 the outcome is not unknown: the check threw on purpose and no `COMMIT` was sent. The same applies to a failed `pg_notify`. In the dispatcher this sets `CommitWatch.Reached = true` (`OutboxDispatch.cs:206`) for a batch that definitely rolled back, so that batch does not halve its size (`OutboxDispatch.cs:129`).
**Why it matters**: Outbox itself adds no after commit action, so PUB-3 is safe today. But any other after commit action in the same transaction (a cache drop, a later module action) now runs for a transaction PUB-3 refused, and a persistent `pg_notify` failure (a dead connection) defeats the DSP-5 halving. The new test (`OutboxPublishTests.cs:184`) checks signals, rows, and the metric, but not after commit actions.
**Suggested fix**: Mark the refusal the way `_refusedCommit` marks the synchronous one (a flag set before the checks and the notifies, cleared when the `COMMIT` starts), so a failure that happened before the commit statement skips the after commit actions. Add a test that registers an after commit action and then trips PUB-3. If I misread EF and the committing call is outside the try, drop this finding; the test will show it.

### 🟡 A rolling upgrade can discard events for good, `server/src/Orvano.Infrastructure/Outbox/OutboxDispatch.cs:171`

**Problem**: A row whose type the running process does not register is marked dispatched with no delivery (DSP-4). DSP-4 describes a rollback, but the same thing happens on a rolling upgrade: a new `api` instance publishes `auth.user.created.v2`, and an old `worker` that is still running does not register it, so it marks the row dispatched with a Warning and the event is gone. No new worker will ever see it.
**Why it matters**: Events are lost without any failure, only a Warning, in the ordinary deploy path of a self hosted install. This is a design choice in the spec, not a coding slip, so I rate it Minor, but it deserves a decision.
**Suggested fix**: Raise it with /architect. Options: leave unknown rows undispatched and only skip them (with a rate limited Warning) until the retention cleanup deletes them, or hold them for a grace period. The cleanup already deletes only dispatched rows, so it would need to cover this case too.

## Nits

- ⚪ `server/tests/Orvano.Testing/JobsDriver.cs:44`, `DispatchAsync` returns 0 when a batch fails (the failure is only logged), so `RunDueAsync` ends as if there were nothing to dispatch and a module test fails later with a confusing assertion. Consider an option or log capture that surfaces a failed batch to the test.
- ⚪ `server/src/Orvano.Infrastructure/Outbox/OutboxDispatch.cs:128`, each failed batch logs twice at Error (EF's command failure and event 10202), as the verify report notes. A poison row at the head of an outbox gives two Error lines per poll. Either log 10202 without the exception when EF already logged it, or drop one level.
- ⚪ `server/src/Orvano.Infrastructure/Jobs/JobExecutor.cs:373`, outside this range but listed in the verify report: the "attempt failed" Warning formats the next run time with the current culture. Pass the invariant culture or log the value as a parameter.
- ⚪ `server/tests/Orvano.ArchitectureTests/ModuleIsolationTests.cs:206`, the `\b[a-z][a-z0-9_]*\.outbox\b` scan also matches a member access such as `handler.outbox` or a comment. Fine for now; if it ever fires on a false positive, narrow it to string literals.
- ⚪ `server/src/Orvano.Infrastructure/Outbox/OutboxDispatch.cs:253`, `WriteRawValue` validates the payload on every row. `jsonb` already guarantees valid JSON, so `skipInputValidation: true` would save a parse of up to 64,000 bytes per event, but keeping the validation is also a defensible safety net. Author's choice.

## Strengths

- The dispatch transaction is right. Claim, delivery inserts, and the mark share one `InTransactionAsync` on one `JobsDbContext`; ordering is left to PostgreSQL (no .NET re-sort of uuids); the rollback tests cover a failure after the inserts and a failure partway through them (`OutboxDispatchTests.cs:130`, `:184`).
- Unknown commit outcome is handled correctly: the `CommitWatch` flag is set by the after commit action, so an unknown outcome neither halves the batch nor loses the event, and the per delivery dedupe key makes the retry safe (DLV-4). The key `<event id>:<subscriber>` is unique per kind and project, and a kind never collides across projects because the row's project never changes.
- Deadlines are consistent with the lessons of #46, #48, and #56: each batch runs under `BatchBound` on the injected `TimeProvider`, linked to the stopping token; the loop wait uses the stopping token; the cleanup runs under the job's own timeout token; the one unbounded step (the rollback on a stalled connection) is named and accepted in DSP-5.
- Shutdown order is correct and tested: `OutboxDispatcher` is registered before `JobRunner`, so the host stops the runner (and its releases and in flight handlers, which may still publish) first, and the dispatcher's wake subscription is created in its constructor so no wake is missed (WAK-5). The runner's always on poll is the single fallback.
- SQL safety is careful: the schema is checked at registration and again in `OutboxSql`, quoted, and the only non constant identifier; every value is a parameter; an architecture test also bans the database clock in `Outbox/` (OTS-1) and all time goes through `TimeProvider`.
- PUB-2 and PUB-3 are strict and in the spec's order: type and CLR type, project id, payload size, `EnsureEnlistable` (open transaction, not joined), own schema, table present; and the check at commit stops an event that was added but never saved from sending its signal.
- Cleanup is bounded and idempotent: 5,000 row chunks each in their own transaction through the primary key, a uuid v7 floor that is correct in PostgreSQL's byte order and unit tested, and one failing outbox does not stop the others.
- Telemetry follows OTL-1: tags come from registrations (`type`, `outbox`), never from row text or ids; metrics count only confirmed commits; payloads are logged only at Debug.
- The DLV-2 workaround for `InternalsVisibleTo` (writing the envelope by hand with `Utf8JsonWriter` and a test that the subscriber's kind reads it back) is clean and keeps SharedKernel's internals closed (RSV-1).
- The pool rule change is consistent across `DatabaseOptions` (`Range(6, 1000)`), `JobConcurrency`, `JobOptions` docs, and the error message, and a test runs a worker on the smallest pool of 6.

## Test coverage

Strong. Covered: publish refusals (PUB-2 and SND-5 cases), rollback and execution strategy retry, the PUB-3 refusal, 250 events in batches of 100, unknown types and no subscribers, halving down to 1 and back to 100 per outbox, a batch cut by the bound, a shutdown mid pass, two dispatchers on 300 events with exactly one job per subscriber per event, project scoping, caller and project in the subscriber scope (AC-38), retry and dead outcomes, a late subscriber, cleanup chunking and partial failure, the module bans and source scan, the pool of 6, host role registration order, and signal and double poll wakes across hosts.

Gaps, all small: no test with a compact many member payload near 64,000 bytes through a real `jsonb` round trip (Minor 1); no test that an after commit action does not run when PUB-3 refuses the commit (Minor 3); no test of a short batch under contention for events with no subscriber (Minor 2).
