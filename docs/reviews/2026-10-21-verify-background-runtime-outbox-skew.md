## How the probes ran

A startup hook (`DOTNET_STARTUP_HOOKS`, built in the session scratchpad outside the repo and deleted with it) loaded
into the real `orvano serve` process from this commit's `Orvano.Host` output, role `worker`, `PollInterval` 2 s.
With `PROBE_ROLE=old` it registered the `sample` outbox with `sample.note.added.v1` and a subscriber
`sample.note_added.record`, plus the `emptybox` outbox with no events. With `PROBE_ROLE=new` it registered `sample`
with v1 and `sample.note.added.v2` and a second subscriber `sample.note_added_v2.record`. The `sample` tables came from
the context's `GenerateCreateScript()`. Each handler wrote a `probe_ran` row (subscriber, event id, type, process id).
A `MeterListener` in the hook printed every `orvano.infrastructure.outbox.*` measurement with its tags to stderr, so
the metrics were read from the real process. Rows were inserted with `psql` in one commit each, so their `id` order was
fixed before any pass saw them; held row locks kept a dispatcher off rows the cleanup probe needed waiting. Every
process and the container were stopped afterwards.

## For /check review and /architect

1. **An old worker claims a new subscriber's delivery jobs and fails them.** DSP-4 keeps the event safe, but once the
   new worker enqueued the 7 v2 deliveries, the old worker's runner claimed each of them at least once and failed it with
   `no handler registered for kind` (Warning 10104), as OUT-2 and CLM-1 specify for an unregistered kind. The new
   worker then ran all 7, at attempt 2 or 3. That is fine at the default 10 attempts, but a new subscriber with a low
   `MaxAttempts` (2, say) could go `dead` during a rolling upgrade before a new worker claims it, which is the loss
   DSP-4 set out to prevent, one layer down. Worth a sentence in DSP-4 or OUT-2, or a claim filter on registered kinds
   like the outbox's, when rolling upgrades come in (spec 0007 RUN-7 puts them after beta).
2. **A registered outbox without a table fails `outbox.cleanup` every day.** The dispatcher skips an outbox with no
   types (DSP-4), but the cleanup still runs OCL-1 on it: `relation "emptybox.outbox" does not exist`, three attempts,
   then `dead`, while the other outbox was cleaned first (OCL-1's per outbox rule held). Only a hand made state can
   cause this (a real module's table comes from `migrate`). Related: for an outbox with no types, OCL-3's
   `NOT (type = ANY('{}'))` matches every waiting row, so such an outbox loses all of its waiting rows after 30 days.
   That follows the rule as written, and is likely what you want, but nothing tests it.
3. Batch counting under skew is as specced: a batch that skips unregistered rows counts only the rows it selected, so
   100 selected rows start another round (seen above as 100 then 96 in one pass).
