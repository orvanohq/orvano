## Summary

Spec 0007 decided that Orvano's server instances tell each other about changes over PostgreSQL's `LISTEN/NOTIFY` (a built in message channel), but left open the exact code contracts and how a signal rides along with the database write it announces. This spec settles both for feature 61's first milestone (signals and cache invalidation). A module hands a signal or a cache tag to the `DbContext` (the database session object) whose transaction is open; the signal is written into that transaction just before it commits, so it goes out only if the change does, and the writer's own cache entry is removed as soon as the commit returns. Each instance runs one listener that applies incoming cache tags, falls back to reading the database whenever it might have missed a signal, and gives later features (the job runner, session revocation) a small plug in point. A review on 2026-10-19 tightened the edges: a slow handler is cut off after 10 seconds and a lagging loop counts as disconnected, a flapping connection backs off, observers hear "disconnected" at boot, only confirmed commits count as sent, a context that only joined a transaction cannot enlist, and modules cannot reach raw connections or the undecorated cache. Milestone 2 adds the job queue: a module hands a job to `IJobQueue` on the same `DbContext` whose transaction is open, so the job row is written by that transaction and a `job` signal wakes the workers only if it commits. Workers claim due jobs with `FOR UPDATE SKIP LOCKED` (a lock that skips rows another worker holds), hold each with a lease they renew while the handler runs, retry failures with backoff, and mark a job dead after its last attempt. Schedules are declared in code, synced into `jobs.schedule` at worker start, and fire exactly once across workers through the job's unique dedupe key. Every time the runner reads comes from the injected clock, so tests drive it. Milestone 3 adds the module outbox: a module publishes a versioned event record through `IOutbox` on its own `DbContext`, which adds a row to its `<module>.outbox` table in the caller's `SaveChanges` and transaction and enlists the `job` signal. A dispatcher loop on each worker, woken by the same wakes as the runner (`WorkerWake`), claims undispatched rows with `FOR UPDATE SKIP LOCKED` and, in the same transaction, enqueues one job per subscriber (each subscriber is its own job kind, with the event copied into the job) and marks the rows dispatched. Subscribers run as ordinary jobs, at least once, unordered, with the job queue's retries. A daily schedule deletes dispatched rows after 7 days.

## Requirements

**User stories**:

- As the engineer of features 9, 13, and 14, I want one small, fixed contract for "invalidate this cache tag everywhere" and "tell every instance about this", so that my module code never touches the listener or `pg_notify`.
- As a self hoster running two replicas, I want a change made through one replica to show on the other on the next request, and a dropped signal connection to cost speed, not correctness.
- As the engineer of the job runner and session revocation, I want to be told when signals may have been lost and when they flow again, so that I can catch up without my own timers for it.
- As the engineer of features 13, 14, 15, and 29, I want to queue work in the same transaction as the change that needs it, with one small contract and a handler per job type, so that the work runs if and only if the change committed, even when the request ends or the process dies.
- As a self hoster running several workers, I want each job to run on one worker at a time, a crashed worker's job to be picked up again, and a recurring job to fire once per tick no matter how many workers run, so that adding replicas never runs work twice on purpose.
- As an operator, I want failing jobs to back off and finally stop as `dead` with their last error, and the runner's state in metrics and logs, so that one bad job type cannot spin forever and I can see what failed.
- As the engineer of a module that announces something (features 13, 14, and later 33 to 36), I want to publish a versioned event in the same transaction as my change, with one call, so that other modules hear about it if and only if the change committed, without my module knowing who listens.
- As the engineer of a module that reacts to another module's events, I want to register one idempotent handler per event type and have it run as a job with retries, in the event's project scope, so that a failure in my handler never blocks the publisher or other subscribers.

**Acceptance criteria**:

- **AC-1**: `Orvano.SharedKernel` exposes `SignalKind`, `ISignalBus`, `ICacheInvalidator`, `ISignalHandler`, `ISignalConnectionObserver`, `ISignalConnectionState`, and the `AddSignalHandler<T>` and `AddSignalConnectionObserver<T>` registrations, with the signatures in _API surface_; `Orvano.Infrastructure` implements them and `Orvano.Host` registers them (spec 0007 REP-2). No module references `Orvano.Infrastructure` (existing architecture test) (BUS-1 to BUS-5).
- **AC-2**: A signal enlisted on a `DbContext` with an open transaction is sent with `pg_notify('orvano_signal', …)` on that transaction's connection just before it commits: nothing is visible to a listener before the commit, a rolled back transaction sends nothing, and a committed one sends exactly one notification per kind, carrying every value enlisted for that kind once, in first enlisted order. Rows changed by `ExecuteUpdate`, `ExecuteDelete`, or raw SQL inside the same transaction are covered the same way (SND-1 to SND-4).
- **AC-3**: Enlisting on a context with no open transaction, or on a context not set up with `UseOrvanoConventions` (so not the platform database), throws `InvalidOperationException` whose message names `InTransactionAsync` (or, for the second case, says only platform database contexts send signals); nothing is sent. Enlisting on a context whose current transaction it joined with `UseTransaction` (rather than began) also throws `InvalidOperationException`, naming the context that began it. Committing with a non empty batch through the synchronous `Commit` also throws, before the commit (SND-5, SND-8).
- **AC-4**: Under the execution strategy (spec 0002 DAT-8), an attempt that enlists values and then fails sends nothing; the retry that commits sends exactly one notification per kind with only its own values, also when the retry reuses the same connection. `InTransactionAsync` runs the work in a fresh transaction per attempt, rolls back explicitly on failure, and clears the change tracker before each retry (SND-3, SND-6).
- **AC-5**: Payloads are `{"v":1,"k":"<kind>","d":[…]}` and at most 999 bytes as encoded. A `cache` or `session` batch whose payload would be larger, or that holds `"*"`, is sent as `["*"]`; `job` carries `[]`. A received payload that is malformed, has another `v`, or names an unknown kind is logged at Warning and ignored without stopping the listener (SND-7, LSN-6).
- **AC-6**: On the writer's own instance, the enlisted cache tags are removed from the local `HybridCache` after the commit succeeds and before `CommitAsync` returns, so a read on that instance right after the commit runs the factory again. They are also removed when the commit fails with an unknown outcome. A rolled back transaction removes nothing (CAC-3, SND-3).
- **AC-7**: With two server hosts on one database, a cache tag invalidated in a committed transaction on host A is removed from host B's cache within 5 seconds, and the next read on host B returns the new value. This is the path spec 0012 AC-10 tests (CAC-4).
- **AC-8**: When the listener connection drops (for example `pg_terminate_backend`) or no `hb` signal arrives for `HeartbeatTimeout`, the instance counts as disconnected at once: `ISignalConnectionState.IsConnected` is false, `HybridCache` reads skip the cache (they run the factory, coalesced only with identical calls already in flight, and store nothing), each observer's `OnDisconnectedAsync` runs once, and `OnFallbackPollAsync` runs right away and then every `FallbackPollInterval` until reconnect. The same happens when the dispatch loop falls behind: an item queued since the current connect that has waited longer than `HeartbeatTimeout` without finishing counts as a disconnect. `/health/ready` stays healthy (LSN-3, LSN-4, LSN-8, CAC-2, HND-3).
- **AC-9**: The instance starts disconnected and says so at boot: before the first connect attempt the listener queues each observer's `OnDisconnectedAsync` once and starts the fallback poll, so a slow or failed first connect never leaves an observer unloaded. The first connect attempt is immediate. While disconnected the listener retries with exponential backoff and full jitter (LSN-5), capped at `ReconnectBackoffCap`. On every successful connect, the first included, it runs `LISTEN orvano_signal`, clears the whole local cache, sets `IsConnected` to true, then runs each observer's `OnConnectedAsync`. The attempt count resets only after a connection has stayed up for `HeartbeatInterval`; a connection that drops sooner counts as a failed attempt, so a flapping connection backs off instead of reconnecting (and clearing the cache) at full speed (LSN-2, LSN-5, HND-3).
- **AC-10**: Each received `cache`, `session`, or `job` signal reaches every `ISignalHandler` registered for its kind, in arrival order and registration order, on a dispatch loop separate from the connection read loop. A handler or observer that throws, or is still running after `HandlerTimeout`, is logged at Error and does not stop other handlers or the listener; a call past the limit is cancelled and abandoned (HND-1, HND-2, HND-4, LSN-6).
- **AC-11**: `SignalOptions` binds from `ORVANO_SIGNALS__HEARTBEATINTERVAL` (default 30 s), `__HEARTBEATTIMEOUT` (90 s), `__RECONNECTBACKOFFCAP` (30 s), `__FALLBACKPOLLINTERVAL` (5 s), and `__HANDLERTIMEOUT` (10 s). Each must be at least 1 second, the heartbeat timeout at least twice the interval, and the handler timeout at most the heartbeat timeout; a bad value stops startup with a message naming the variable (spec 0002 CFG-1, CFG-4) (SOP-1, SOP-2).
- **AC-12**: Modules cannot call `HybridCache.RemoveAsync` or `HybridCache.RemoveByTagAsync` (banned symbols); they invalidate only through `ICacheInvalidator`. They also cannot use `TransactionSignals`, `SignalPayload`, `NpgsqlConnection.Notification`, `Wait` or `WaitAsync`, or open connections from an `NpgsqlDataSource`, no module source file contains `pg_notify` or `orvano_signal`, and the undecorated cache is registered under a key modules cannot name (CAC-1, CAC-5). Only `serve` runs the listener, in every role; other commands get the cache, the invalidator, and the interceptor with the listener absent, so their cache stays bypassed (CAC-5, LSN-1).
- **AC-13**: The listener's state and traffic are observable: Information logs on connect, Warning on disconnect and on each failed reconnect attempt, and the metrics `orvano.infrastructure.signals.connected` (observable gauge, 1 or 0), `orvano.infrastructure.signals.sent` and `orvano.infrastructure.signals.received` (counters tagged `kind`, `hb` not counted; `sent` counts only confirmed commits, never an unknown commit outcome), and `orvano.infrastructure.cache.clears` (counter tagged `reason`: `connect` or `wildcard`) (LSN-7).

**Acceptance criteria, milestone 2 (job queue, runner, and schedules)**:

- **AC-14**: `Orvano.SharedKernel` exposes `IJob`, `IJobHandler<TJob>`, `IJobQueue`, `JobContext`, `EnqueueOptions`, `JobKindOptions`, `PermanentJobFailureException`, `JobAccessScope`, and the `AddJobHandler<TJob, THandler>` and `AddJobSchedule<TJob>` registrations, with the signatures in _Job queue API surface_; `Orvano.Infrastructure` implements them and `Orvano.Host` registers them. No module references `Orvano.Infrastructure` (JQ-1 to JQ-6).
- **AC-15**: `orvano migrate` creates `jobs.job` and `jobs.schedule` through `JobsDbContext`, first in `MigrationOrder`, with exactly the columns, CHECK constraints, indexes, and storage parameters in _Job tables_; `HasPendingModelChanges()` is false, and the spec 0011 architecture tests pass for the new context (JDB-1 to JDB-4).
- **AC-16**: `EnqueueAsync(context, job, options, cancellationToken)` inside an open platform transaction inserts one `queued` row on that transaction's connection: no other connection sees it before the commit, a rollback leaves none, and an execution strategy retry leaves exactly one. The transaction sends one `job` signal (`[]`) on commit when at least one job it enqueued is due (`run_at` at or before now), and none when every job it enqueued is in the future or was a dedupe hit. It returns the new id, or `null` when a row with the same `kind`, `project_id` (no project matches no project), and `dedupe_key` exists in any status; the same key under another kind or another project inserts (ENQ-1 to ENQ-5, JDB-2).
- **AC-17**: `EnqueueAsync` with a context throws `InvalidOperationException`, and inserts nothing, when the context has no open transaction, is not a platform database context, or joined its transaction with `UseTransaction` (the SND-5 messages). Both overloads throw `InvalidOperationException` for a kind with no registered handler, and `ArgumentException` for a payload over 65,536 UTF-8 bytes, a dedupe key outside 1 to 200 characters, or an empty project id (ENQ-2, ENQ-3).
- **AC-18**: `EnqueueAsync(job, options, cancellationToken)` with no context commits its own transaction on a fresh `JobsDbContext` and sends the `job` signal the same way; the caller's context, if any, is untouched (ENQ-6).
- **AC-19**: A worker claims at most its free slots in one statement with `FOR UPDATE SKIP LOCKED`: first `queued` rows that are due, in `run_at, id` order, then, while slots remain, `running` rows whose lease expired and that have attempts left, in `locked_until, id` order, and never a job this process is still running. Each claim adds 1 to `attempt` and sets `locked_by` and `locked_until` from the kind's lease. Two workers polling the same 50 due jobs at once run each job exactly once between them, and no worker ever runs more handlers at once than its `Concurrency`, counting timed out handlers that have not returned (CLM-1 to CLM-3).
- **AC-20**: While a handler runs, the runner renews its lease every third of the kind's lease, one renewal at a time, each a single attempt bounded by lease ÷ 3. A renewal or an outcome write that finds the row no longer held by this worker and attempt (lease lost) cancels the handler's token and writes nothing. The renewal is stopped and awaited before the outcome write, so a job that succeeded is never counted as a lost lease. A job whose worker stopped renewing (process killed) is claimed again after `locked_until` passes, and one whose expired lease was on its last attempt becomes `dead` with `last_error` saying so at the next poll tick (or `JobsDriver` pass), without running again; a signal wake or a freed slot claims without running the dead marking (CLM-1, CLM-4 to CLM-6, OUT-4, WAK-2).
- **AC-21**: A handler that returns marks the job `succeeded` with `finished_at`. One that throws, runs past the kind's `Timeout`, has a kind with no registered handler, or has a payload that does not deserialize puts the job back to `queued` with `run_at` = now + a delay between d / 2 and d, where d = min(1 hour, 10 s × 2^(attempt − 1)), and the error in `last_error`; at `attempt` = `max_attempts` it becomes `dead`. `PermanentJobFailureException`, and a job of a kind with `RequiresProject` but no `project_id`, make it `dead` at once. A timed out handler keeps its slot until it returns. A job cancelled by host shutdown goes back to `queued`, due now, with `attempt` restored, and a handler that finishes during shutdown still records its outcome. A cancellation's cause is judged in the order lease lost, timed out, shutdown (OUT-1 to OUT-8).
- **AC-22**: With `PollInterval` set to 1 minute, a due job enqueued and committed through host A (role `api`) starts on host B (role `worker`) within 2 seconds, woken by the `job` signal. With host B's signal connection terminated, it starts within one `PollInterval`. A job enqueued with a future `run_at` starts within one `PollInterval` after `run_at`. On every signal connect, the runner claims at once (WAK-1 to WAK-4).
- **AC-23**: A job with `project_id` runs in a DI scope whose `ICallerContext.Current` is `Caller.System` and whose `IProjectContext.Id` equals the job's `project_id`; a job without one has `Caller.System` and `IProjectContext.Id` throws. `JobContext` carries the id, kind, attempt, max attempts, project id, `run_at`, and `created_at` from the row (CLM-7, JQ-2).
- **AC-24**: A bad schedule or kind registration stops startup with a clean message naming it and exit code 1, never an unhandled exception: a bad name or out of range `JobKindOptions` when it is registered, and, when `StartupChecks` builds `JobRegistry`, a cron expression `Cronos` cannot parse in its five field format or that has no next occurrence, a duplicate name or kind, a schedule whose kind has no registered handler or has `RequiresProject`, or a schedule payload over 65,536 bytes. At worker start the runner upserts every registered schedule in name order and deletes rows for names no longer registered. Two workers ticking at the same instant fire a due schedule exactly once, as a job with `dedupe_key` `<name>:<fire time as yyyyMMddTHHmmssZ>`; a schedule whose fires were missed while no worker ran fires once, then moves `next_run_at` to the next occurrence after now; changing a schedule's cron recomputes `next_run_at`; a disabled schedule never fires; a schedule tick that fails does not stop the claim after it (SCH-1 to SCH-6).
- **AC-25**: The built in `jobs.cleanup` schedule (daily at 03:17 UTC) deletes `succeeded` jobs whose `finished_at` is more than 7 days old and `dead` jobs more than 30 days old, 5000 rows per statement until none remain, which frees their dedupe keys (SCH-7, spec 0007 JOB-3).
- **AC-26**: `JobOptions` binds from `ORVANO_JOBS__POLLINTERVAL` (default 5 s, 1 s to 5 minutes) and `ORVANO_JOBS__CONCURRENCY` (default the smallest of processor count × 2, 16, and half of `ORVANO_DATABASE__POOLSIZE` less two, at least 1; explicit values 1 to 256). An explicit concurrency above half the platform pool less two stops startup with a message naming `ORVANO_JOBS__CONCURRENCY`, `ORVANO_DATABASE__POOLSIZE`, and the largest allowed value, and a pool size below 6 stops startup naming `ORVANO_DATABASE__POOLSIZE` (amended by milestone 3, OPL-1). With every handler holding a platform connection and renewing at once, a request still gets a connection from the pool. Only `serve` with the `worker` role runs the runner, the schedule sync, and the `job` handler; every command can enqueue (JOP-1 to JOP-4).
- **AC-27**: The runner is observable: the metrics `orvano.infrastructure.jobs.enqueued`, `.attempts`, `.duration`, `.lag`, `.running`, and `.schedules.fired` and the log events in JTL-2, with `kind`, `outcome`, and `schedule` tags only (no ids), and each attempt runs in an activity linked to the enqueuing trace. Payloads and dedupe keys never appear in logs above Debug (JTL-1 to JTL-3).
- **AC-28**: Modules cannot set the job access scope or write the jobs schema directly: `JobAccessScope` is in `BannedSymbols.Modules.txt`, the module source scan also fails on `jobs.job` and `jobs.schedule`, and the spec 0012 PRJ-3 architecture test allows `AccessContext.Establish` only from the access layer and `JobAccessScope` (JQ-6, JTS-4).

## Decision

**Chosen option**: Option 1, an explicit `DbContext` argument with a per context batch that a transaction interceptor sends just before commit; the writer removes its own entries once the commit returns; a `HybridCache` decorator gives modules the disconnect bypass without code changes.

Modules call `ICacheInvalidator.Invalidate(db, tags)` or `ISignalBus.Enlist(db, kind, values)` inside an open platform database transaction, normally through `InTransactionAsync`; the batch starts empty with every transaction, so retries, rollbacks, and several module contexts in one request each behave by construction.

**Milestone 2 chosen option**: Option J1 in [rationale.md](rationale.md#milestone-2-job-queue-2026-10-19), Infrastructure writes the job row with SQL on the caller's own `DbContext` connection and enlists the `job` signal on that context, so the job joins the caller's transaction through the same SND machinery as a signal; a context free overload runs its own transaction on `JobsDbContext`. Jobs are typed records with a static `Kind`, each kind has one scoped `IJobHandler<TJob>` registered with its JSON type info, and schedules are declared in code and synced into `jobs.schedule` by each worker.

**Milestone 3 chosen option**: Options O1, S1, P1, and I1 in [rationale.md](rationale.md#milestone-3-module-outbox-2026-10-20). `IOutbox.Publish` adds an `OutboxEvent` entity to the caller's own context, so the caller's `SaveChangesAsync` writes it in the open transaction, and a before commit check refuses a commit that left it unsaved (O1). Each subscriber is its own job kind, and the dispatcher copies the event into each delivery job (S1). The dispatcher is a second worker loop on `WorkerWake` with its own pool connection, paid for by lowering JOP-2's limit by one (P1). Its SQL names each outbox table through one registered, pattern checked identifier (I1).

**Implementation skills**: none installed for this area. The `caching` skill named in spec 0007 shows a Redis backplane; spec 0007 CCH-1 and this spec win over it (GEN-0).

## Feature design

### Scope and boundaries

- In: the SharedKernel contracts, the transaction join, the payload codec, the listener (connect, `LISTEN`, heartbeat, timeout, backoff, dispatch), `SignalOptions`, `HybridCache` registration and its decorator, `ICacheInvalidator`, the `cache` handler, the clear on connect, telemetry, and the tests.
- In (milestone 2): the job queue and runner, the `job` handler and its `OnConnectedAsync` wake, and schedules; see _Job queue design_ below.
- In (milestone 3): the module outbox and dispatcher; see _Outbox design_ below. It plugs into the runner through `WorkerWake` (WAK-5) and enqueues through ENQ-1. Out (feature 14): the `session` handler, the revoked session set, and its fallback poll body. They plug into HND-1 to HND-3.
- Out: project databases. They never send signals (spec 0007 SIG-3), which SND-5 enforces.

### Rules

**Contracts (`Orvano.SharedKernel/Signals/`)**

- **BUS-1 (MUST)**: `SignalKind` is a public enum `Job`, `Cache`, `Session`, sent on the wire as `job`, `cache`, `session`. The `hb` kind is internal to the listener and is not in the enum.
- **BUS-2 (MUST)**: `ISignalBus.Enlist(DbContext context, SignalKind kind, IEnumerable<string> values)` is synchronous and does no I/O; it adds the values to the context's batch (SND-1). Values are 1 to 200 printable ASCII characters (`0x21` to `0x7E`, so no spaces or control characters), else `ArgumentException`. An empty list is a no op for `cache` and `session` and marks `job` present. Modules use it for `session` (feature 14); cache tags go through `ICacheInvalidator` and job wakes through `IJobQueue` (milestone 2). `Enlist` with `SignalKind.Cache` throws `ArgumentException` pointing to `ICacheInvalidator`, because only the invalidator adds the writer's local removal (CAC-3).
- **BUS-3 (MUST)**: `ICacheInvalidator.Invalidate(DbContext context, IEnumerable<string> tags)` (plus a `params string[]` overload) enlists the tags as a `cache` signal and registers their local removal for after the commit (CAC-3). `"*"` means every entry. There is no variant without a context: every invalidation announces a platform database change, and that change has a transaction (SND-5).
- **BUS-4 (MUST)**: `ISignalHandler` (`SignalKind Kind { get; }`, `ValueTask HandleAsync(IReadOnlyList<string> values, CancellationToken cancellationToken)`) and `ISignalConnectionObserver` (`OnConnectedAsync`, `OnDisconnectedAsync`, `OnFallbackPollAsync`, each `ValueTask (CancellationToken)`, with default bodies that do nothing) are the only hook points (HND-1 to HND-3). `ISignalConnectionState` has `bool IsConnected { get; }`.
- **BUS-5 (MUST)**: `services.AddSignalHandler<T>()` and `services.AddSignalConnectionObserver<T>()` register singletons; they run in registration order. A handler that needs a database creates a scope through `IServiceScopeFactory`.

**Joining the transaction (SND, `Orvano.SharedKernel/Data/`)**

- **SND-1 (MUST)**: The batch (`PendingSignals`: kind to ordered distinct values, after commit actions, on committed actions, and a joined flag) is a scoped EF internal service that `UseOrvanoConventions` registers in `OrvanoOptionsExtension.ApplyServices`, so there is exactly one per `DbContext` instance. `TransactionSignals` (public static) is the only way to reach it: `Enlist(DbContext, SignalKind, IEnumerable<string>)` returns whether this is the first enlist of that kind in the current transaction; `AddAfterCommit(DbContext, Func<CancellationToken, ValueTask>)` adds an action that runs after a confirmed commit and also after a commit with an unknown outcome (use it for anything that is safe to do twice or for nothing, such as a local cache removal); `AddOnCommitted(DbContext, Func<CancellationToken, ValueTask>)` adds an action that runs only after a confirmed commit (use it for anything that must not happen for a commit that may not have gone through, such as counting a signal as sent); `Enlisted(DbContext, SignalKind)` reads the values enlisted so far. Infrastructure's `SignalBus` and `CacheInvalidator` call it; modules use the interfaces, and the modules ban list bans the type (CAC-5).
- **SND-2 (MUST)**: `SignalTransactionInterceptor`, a `DbTransactionInterceptor`, is registered by `UseOrvanoConventions` as a scoped EF service, the same way as `TimestampInterceptor` (spec 0011 AC-3), so every platform context has it with no module code. In `TransactionCommittingAsync` it runs one `SELECT pg_notify('orvano_signal', @payload)` per kind in the batch, on `eventData.Transaction.Connection` with the command's `Transaction` set. A failure there (including PostgreSQL error `25P02` on an aborted transaction) fails the commit, because the signal is part of the change.
- **SND-3 (MUST)**: The batch is cleared in `TransactionStartedAsync` and `TransactionUsedAsync` (so a retry starts empty even when Npgsql reuses its transaction object), and in `TransactionRolledBackAsync`. In `TransactionCommittedAsync` the after commit actions run, then the on committed actions, then the batch is cleared. In `TransactionFailedAsync` only the after commit actions run, and only when the failed action is the commit (`TransactionErrorEventData.Action` is `"Commit"`), because the outcome is unknown and a local removal is always safe; the on committed actions never run there; then the batch is cleared. Both kinds of action run with `CancellationToken.None` (the commit happened, or may have), catch their own exceptions, and `PendingSignals` also catches and logs at Error any that throws anyway; they never fail a commit that happened. A savepoint rollback keeps enlisted values (an extra signal is harmless).
- **SND-4 (MUST)**: Within one batch, values of a kind are deduplicated with ordinal comparison and keep first enlisted order. A `job` enlist only marks the kind present.
- **SND-5 (MUST)**: `Enlist` and `Invalidate` throw `InvalidOperationException` when the context has no open transaction ("Signals join a transaction. Wrap the write in InTransactionAsync (spec 0013 SND-6).") or when `OrvanoConventions.SchemaOf` returns null for the context ("Only platform database contexts send signals (spec 0007 SIG-3)."). They also throw `InvalidOperationException` ("This context joined another context's transaction with UseTransaction. Enlist on the context that began it (spec 0013 SND-5).") when the context's current transaction was joined rather than begun: `TransactionUsed` and `TransactionUsedAsync` set the batch's joined flag, `TransactionStarted` and `TransactionStartedAsync` clear it, and every transaction end clears it. Signals belong to the context that began the transaction, which is also the one that commits it (`InTransactionAsync`, spec 0011 TXN-1). A joined context that commits the shared transaction itself sends nothing and runs no actions for the owner's batch; that pattern is unsupported, and no Orvano path uses `UseTransaction`. A `DbTransaction` committed behind EF's back sends nothing.
- **SND-6 (MUST)**: `OrvanoTransactions.InTransactionAsync<T>(this DbContext db, Func<CancellationToken, Task<T>> work, CancellationToken cancellationToken, IsolationLevel isolation = IsolationLevel.ReadCommitted)` (and a non generic overload) runs `work` inside `CreateExecutionStrategy().ExecuteAsync`, in a transaction it begins and commits with `CommitAsync`, calls `RollbackAsync` when `work` or the commit throws, and calls `db.ChangeTracker.Clear()` before every attempt after the first (entities the caller loaded before the call are discarded on a retry). It throws `InvalidOperationException` when the context already has a transaction. `work` loads and changes everything it saves, and must be safe to run twice: PostgreSQL's retrying strategy cannot tell whether a commit that failed with an unknown outcome went through, so use `xmin` (DAT-9), unique keys, or idempotent statements.
- **SND-7 (MUST)**: `SignalPayload` is pure: `Encode(SignalKind, IReadOnlyList<string>)`, an internal `EncodeHeartbeat()`, and `TryDecode(string, out string kind, out IReadOnlyList<string> values)`, which returns the raw kind text so the listener handles `hb`. Encode writes `{"v":1,"k":…,"d":[…]}` with `System.Text.Json` and its default encoder, and measures the encoded UTF-8 bytes; over 999, or when the values contain `"*"`, a `cache` or `session` batch becomes `["*"]` for the wire and for the local removal. `"*"` for `session` means "reload the whole revoked set" (amends spec 0007 SIG-1). `TryDecode` ignores unknown properties and requires `v` to be 1 and `d` to be an array of strings that each pass BUS-2's value rule (`"*"` included); a `job` with values, or a `cache` or `session` with none, is ignored and logged at Debug.
- **SND-8 (MUST)**: The synchronous `TransactionCommitting` throws `InvalidOperationException` ("Commit with CommitAsync when signals are enlisted.") when the batch is not empty, before anything is sent. Every Orvano path commits asynchronously (spec 0002 ASY-1).

**Listener (LSN, `Orvano.Infrastructure/Signals/`)**

- **LSN-1 (MUST)**: `SignalListener` is a `BackgroundService` registered by `AddSignalListener()`, which only `ServeCommand` calls (every role, spec 0007 RUN-2). `AddInfrastructure` registers the rest (the decorator, `CacheInvalidator`, `SignalBus`, and an `ISignalConnectionState` that reports false until a listener replaces it), so `migrate`, `admin`, and tests without the listener get a bypassed cache and still enlist signals. The listener opens its connection from the keyed `NpgsqlDataSource` `"signals"` that `Orvano.Host` registers from `DatabaseOptions` through the same connection string helper as the platform data source (one helper, extracted from `PlatformDatabase`), with `Pooling=false`, `Keepalive=30`, `Timeout=15`, `CommandTimeout=30` (set explicitly so a library default change cannot move the connect and `LISTEN` bounds), and `ApplicationName=orvano-signals-<instance id>`, where the instance id is 8 random hex characters chosen at startup and readable by tests (`InternalsVisibleTo`).
- **LSN-2 (MUST)**: At the start of `ExecuteAsync`, before the first connect attempt, the listener announces the disconnected state it starts in: it queues `OnDisconnectedAsync` for every observer and starts the fallback poll (LSN-4), exactly as LSN-3 does after a drop, except that there is no connection to close. A failed first connect therefore announces nothing new. On connect it runs `LISTEN orvano_signal`, sets the last heartbeat time to now, clears the cache (CAC-6), sets connected, drops any queued fallback poll, then queues `OnConnectedAsync` for every observer. It then loops on `NpgsqlConnection.WaitAsync(TimeSpan)`, each wait bounded by the earlier of the next heartbeat due time and the timeout deadline. Notifications are handled on the read loop: `hb` updates the last heartbeat time; other kinds go to the dispatch queue.
- **LSN-3 (MUST)**: Between waits, when `HeartbeatInterval` has passed since the last send, it sends `hb` on its own connection (PostgreSQL delivers a session's own notifications to it) through an internal `IHeartbeatSender`, which tests may replace with one that sends nothing. A heartbeat from any replica counts. When `HeartbeatTimeout` passes with none, or any I/O on the connection fails, it sets disconnected at once on the read loop (so the cache bypass starts before any queued work), closes the connection, queues `OnDisconnectedAsync`, and starts the fallback poll timer and the reconnect loop.
- **LSN-4 (MUST)**: The fallback poll queues `OnFallbackPollAsync` for every observer immediately on disconnect and then every `FallbackPollInterval` until connected. At most one poll is queued at a time; a tick that finds one still queued is skipped.
- **LSN-5 (MUST)**: The first attempt (at startup, or right after a disconnect) is immediate. After failed attempt n it waits a random delay between 0 and min(`ReconnectBackoffCap`, 1 s × 2^(n − 1)) (full jitter). A connect counts as a success, and n resets to 0, only once the connection has stayed connected for `HeartbeatInterval` (the listener records when it connected and resets n at the first loop pass past that time). A connection that drops sooner counts as failed attempt n + 1, so the next attempt waits; only a drop after a stable connection takes the immediate first attempt. No new option: the stable period is `HeartbeatInterval`, which is also the earliest point a missing heartbeat can be noticed. All waits and timers use the injected `TimeProvider` (spec 0002 GEN-9, ASY-7).
- **LSN-6 (MUST)**: The dispatch queue is an unbounded `Channel` read by one loop, so handlers and observers run one at a time, in arrival order, and in registration order within one item. Each call gets a token linked to the host's stopping token that cancels after `HandlerTimeout` (SOP-1), and the loop waits on the call no longer than that, so a call that ignores its token cannot hold the loop: at the limit the call is abandoned (its later exception observed and logged at Debug), an Error is logged with the kind or observer method and the type, and the loop moves to the next call. An exception is logged at Error with the kind and handler type and the loop continues; an `OperationCanceledException` during shutdown is not logged. Anything else that faults while handling one item is caught per item and logged at Error, so the loop itself never ends while the host runs. A queue longer than 1000 items logs a Warning at most once per minute. Malformed or unknown payloads are logged at Warning and dropped (AC-5). On shutdown the listener stops reading, sets disconnected, drops the queue, and closes its connection.
- **LSN-7 (MUST)**: Telemetry lives in `InfrastructureTelemetry` (meter and activity source `Orvano.Infrastructure`, spec 0002 LOG-5) and `InfrastructureLog`, with a new event ID block `LogEventIds.Infrastructure = 10000`. `signals.sent` is counted by an on committed action (SND-1) that `SignalBus` adds once per kind per transaction, so only confirmed commits count and a commit with an unknown outcome is not counted (it may or may not have sent; the EF commit failure log already records it). `signals.received` is counted on the read loop, and `cache.clears` with `reason=connect` on every connect (the first included) and `reason=wildcard` on a received or committed `["*"]`. No project or user id tags.
- **LSN-8 (MUST)**: A dispatch loop that falls behind counts as disconnected. Each queued item records the connection epoch and the time it was queued. Between waits (at least every `HeartbeatInterval`, LSN-2) the read loop checks the oldest item of the current epoch that has not finished; when it was queued more than `HeartbeatTimeout` ago, the listener takes the LSN-3 disconnect path (bypass on at once, connection closed, `OnDisconnectedAsync` queued, fallback poll, reconnect) and logs a Warning naming the lag. Items from an earlier epoch never count, because the clear on the next connect (CAC-6) already covers any cache signal they carry, so a reconnect behind a stuck call does not flap; the short lived connection rule (LSN-5) backs off if new items keep lagging. The threshold is `HeartbeatTimeout` on purpose: it is the staleness the instance already accepts from a silent connection, and `HandlerTimeout` (at most `HeartbeatTimeout`, SOP-2) keeps one call from reaching it alone.

**Hooks (HND)**

- **HND-1 (MUST)**: The `cache` handler is Infrastructure's own (CAC-4). Milestone 2 adds a `job` handler that wakes the runner; feature 14 adds a `session` handler. Several handlers per kind are allowed.
- **HND-2 (MUST)**: A handler receives the payload's values as sent, including `["*"]`, and decides what that means for its kind.
- **HND-3 (MUST)**: Observers mean: `OnConnectedAsync`, anything sent before now may have been lost, so resync (the runner wakes, the revoked set reloads in full); `OnDisconnectedAsync`, signals may be lost from now on; `OnFallbackPollAsync`, poll the database for what signals would have said (the revoked set loads changes since its last load). Timing comes from the listener (SOP-1), never from the observer.
- **HND-4 (MUST)**: Handlers and observers must be quick or hand their work off; they share one loop. Each call is cut off at `HandlerTimeout` (LSN-6), and a loop that lags past `HeartbeatTimeout` turns the cache bypass on (LSN-8), so a slow hook costs speed and logs Errors but never leaves stale entries served as fresh.

**Cache (CAC)**

- **CAC-1 (MUST)**: `AddInfrastructure` calls `AddHybridCache()` (package `Microsoft.Extensions.Caching.Hybrid` 10.x, MIT) with no `IDistributedCache` (CCH-1), and sets `HybridCacheOptions.DefaultEntryOptions` to `Expiration` and `LocalCacheExpiration` of 60 seconds, so an entry without its own options gets the security cap (CCH-2, PRF-2); key length and payload limits keep their defaults. It then moves the default `HybridCache` registration to a keyed service and registers `SignalAwareHybridCache` as the unkeyed singleton over it. The decorator overrides the abstract members (`GetOrCreateAsync<TState, T>`, `SetAsync<T>`, `RemoveAsync(string)`, `RemoveByTagAsync(string)`) and the `IEnumerable<string>` removal overloads. The key is an `internal static readonly object` sentinel in `Orvano.Infrastructure` (`SignalAwareHybridCache.InnerKey`), not a string, so a module cannot resolve the undecorated cache with `[FromKeyedServices]`; Infrastructure's own consumers (`CacheInvalidator`, the `cache` handler, the clear on connect) resolve it with that key. Modules inject `HybridCache` as usual. Cached types are immutable records (sealed, or marked `[ImmutableObject(true)]`) or serializable with `System.Text.Json`, because HybridCache copies mutable values through its serializer.
- **CAC-2 (MUST)**: While `IsConnected` is false the decorator adds `HybridCacheEntryFlags.DisableLocalCacheRead | DisableLocalCacheWrite` to every `GetOrCreateAsync` and `SetAsync`. It builds new entry options that keep the caller's expiry values and combine the flags with the caller's (or, when the caller's `Flags` is null, with `DefaultEntryOptions.Flags`); tags pass through unchanged. Removals always pass through.
- **CAC-3 (MUST)**: `CacheInvalidator.Invalidate` enlists the tags through `ISignalBus` (BUS-3) and, on the first cache enlist in the transaction, adds one after commit action that calls the inner cache's `RemoveByTagAsync` with every tag enlisted in that transaction (or `"*"`, SND-7). Nothing is removed before the commit: a reader could otherwise refill the entry from the old, still committed row.
- **CAC-4 (MUST)**: The `cache` handler calls `RemoveByTagAsync` with the received tags on every instance, the writer included. A reader that loaded the old row before the commit and stores it after both removals keeps a stale entry until it expires (at most 60 seconds for security related entries); applying the writer's echo too narrows that window but cannot close it. That bound is the accepted risk of a cache without row versions (CCH-2).
- **CAC-5 (MUST)**: A modules only banned symbols file, `server/src/BannedSymbols.Modules.txt`, added by `Directory.Build.props` for projects whose name starts with `Orvano.Modules.`, bans `HybridCache.RemoveAsync` and `HybridCache.RemoveByTagAsync` (the `string` and `IEnumerable<string>` overloads) with the reason "invalidate through ICacheInvalidator (spec 0013 CAC-5)". It also bans, each with its rule ID in the reason: `T:TransactionSignals` and `T:SignalPayload` (SND-1, SND-7: enlist through the interfaces); `E:NpgsqlConnection.Notification` and every public `NpgsqlConnection.Wait` and `WaitAsync` overload (LSN-1: only the listener listens); and `NpgsqlDataSource.OpenConnection`, `OpenConnectionAsync`, `CreateConnection`, `CreateCommand`, and `CreateBatch` (a module writes the platform database through its `DbContext`, so its signals join the transaction, and reaches project databases only through `IProjectDbConnectionFactory`, spec 0007 PG-3). The architecture test that checks the removal overloads by reflection also checks these lists cover every public overload of the named members. A second architecture test fails when any `.cs` file under `server/src/Orvano.Modules.*` contains `pg_notify` or `orvano_signal`, case insensitive, which no symbol ban can catch in raw SQL text.
- **CAC-6 (MUST)**: Clearing everything (each connect, or a received `["*"]`) is `RemoveByTagAsync("*")`, HybridCache's reserved tag for all entries. No module may use `"*"` as a real tag. A test proves the clear removes entries with and without tags on the pinned package version.

**Options (SOP)**

- **SOP-1 (MUST)**: `SignalOptions` in `Orvano.Infrastructure/Signals/` (`Section = "Signals"`): `HeartbeatInterval` 30 s, `HeartbeatTimeout` 90 s, `ReconnectBackoffCap` 30 s, `FallbackPollInterval` 5 s, `HandlerTimeout` 10 s (the longest one handler or observer call may run, LSN-6), each a `TimeSpan` with an XML doc comment (CFG-1). `HandlerTimeout` is its own option, not `HeartbeatTimeout`, because a 90 second stall is far too long for cache freshness, while 10 seconds still fits an observer's fallback poll query on a healthy database; a poll cut short is retried on the next tick.
- **SOP-2 (MUST)**: A source generated validator requires each to be at least 1 second, `HeartbeatTimeout` at least twice `HeartbeatInterval`, and `HandlerTimeout` at most `HeartbeatTimeout` (so one call alone never trips the lag rule, LSN-8). Tests shorten them through `OrvanoApiFactory` settings, and stop heartbeats with the `IHeartbeatSender` seam (LSN-3); operators normally leave them alone.

### Data model sketch

No tables. The state is in memory per process:

| Thing                                                                                                                      | Where                                                          | Lifetime                                                                                              |
| -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Pending batch (`PendingSignals`: kind to ordered distinct values, after commit actions, on committed actions, joined flag) | scoped EF internal service, one per `DbContext` (SND-1, SND-5) | cleared at every transaction start, use, commit, rollback, or failure (the joined flag is set at use) |
| Connection state (`IsConnected`, last heartbeat time, attempt count, connected since, epoch)                               | `SignalListener`, exposed as `ISignalConnectionState`          | process                                                                                               |
| Dispatch queue (each item: epoch and time queued)                                                                          | unbounded `Channel` in `SignalListener` (LSN-6, LSN-8)         | process                                                                                               |

### State transitions

Listener: `Disconnected` (start, announced to observers before the first attempt) → `Connecting` → `Connected` → (`hb` timeout, I/O error, or dispatch lag) → `Disconnected` → `Connecting` … → `Stopped` on host shutdown. `Connected` is entered only after `LISTEN` succeeded and the cache was cleared. The cache bypass is on in every state except `Connected`. A `Connected` spell shorter than `HeartbeatInterval` counts as a failed attempt for backoff (LSN-5).

Pending batch: emptied at transaction start (or at use, which also marks it joined and refuses enlists) → filled by enlists → sent at `TransactionCommitting` → after commit actions then on committed actions run at `TransactionCommitted`, or only after commit actions at a failed commit → emptied; or emptied at rollback.

### Key invariants

- A notification is visible only after its transaction commits, and at most one per kind per transaction (SIG-3).
- A rolled back attempt sends nothing and removes nothing; every transaction starts with an empty batch.
- Whenever an instance might have missed a signal (before the first connect, while disconnected, or with no listener at all), its cache is bypassed; on every connect the whole cache is cleared before the bypass turns off.
- Payloads carry ids and tags only, never data or secrets, and stay at most 999 encoded bytes.
- Project database contexts can never enlist a signal.

### Security model

No caller facing surface. The channel is on the platform database, reachable only with the platform owner role (spec 0007 PG-2a); any session with that role could send a forged `cache` signal, which at worst empties caches (more database reads, never wrong answers), and a forged `session` signal can only revoke, never grant. Payloads hold tags and ids only. Permission answers stay uncached (CCH-2), and the 60 second default expiry (CAC-1) keeps an entry with no explicit options inside the security cap. Logs never include payload values above Debug (they hold user ids).

### Configuration required

- `ORVANO_SIGNALS__HEARTBEATINTERVAL` (30 s): how often each instance sends `hb`
- `ORVANO_SIGNALS__HEARTBEATTIMEOUT` (90 s): silence after which the instance counts as disconnected
- `ORVANO_SIGNALS__RECONNECTBACKOFFCAP` (30 s): the longest wait between reconnect attempts
- `ORVANO_SIGNALS__FALLBACKPOLLINTERVAL` (5 s): how often observers poll while disconnected
- `ORVANO_SIGNALS__HANDLERTIMEOUT` (10 s): the longest one signal handler or observer call may run before it is cut off

### Critical test scenarios

- Happy path: two `OrvanoApiFactory` hosts on one database; host A caches an entry tagged `t`, host B caches one tagged `t`; host A runs `InTransactionAsync` that updates a row and invalidates `t`; host A's entry is gone when `CommitAsync` returns, host B's within 5 s; verifies **AC-6**, **AC-7**.
- Join: a raw `LISTEN` connection in the test sees nothing before commit, one notification per kind after it, none after a rollback, and none for an `ExecuteUpdate` in a rolled back transaction; verifies **AC-2**.
- Refusal: `Invalidate` with no transaction and on a context without `UseOrvanoConventions` throws and sends nothing; a synchronous `Commit` with a batch throws before committing; `InTransactionAsync` inside an open transaction throws; verifies **AC-3**.
- Retry: an attempt that enlists `a` then throws a transient error, followed by a successful attempt on the same connection that enlists `b`, sends exactly one `cache` notification with `["b"]`; a `work` that throws a plain exception leaves no batch behind for the next transaction; verifies **AC-4**.
- Unknown commit: a commit forced to fail after `COMMIT` is sent (connection killed during commit) still removes the writer's local entries; verifies **AC-6**.
- Oversize: 60 tags of 36 characters produce `["*"]`, and the receiving host clears everything; a malformed payload sent by the test is ignored and the next good one applies; verifies **AC-5**, **AC-10**.
- Disconnect: the test runs `pg_terminate_backend` on host A's `orvano-signals-<id>` backend only; host A's reads run the factory every time, observers see one `OnDisconnectedAsync` and repeated `OnFallbackPollAsync`, `/health/ready` is `Healthy`, host B stays connected; after reconnect host A's cache was cleared and `OnConnectedAsync` ran; verifies **AC-8**, **AC-9**.
- First connect fails (database unreachable for the listener only): `OnDisconnectedAsync` runs once and polls start from boot; verifies **AC-9**.
- Heartbeat timeout: with the no op `IHeartbeatSender` on every host and short options, the listener counts as disconnected after `HeartbeatTimeout`; verifies **AC-8**, **AC-11**.
- A throwing handler is logged and the next signal still reaches the other handlers, in registration order; verifies **AC-10**.
- Bad options (`ORVANO_SIGNALS__HEARTBEATTIMEOUT=00:00:30` with a 30 s interval) stop startup naming the variable; verifies **AC-11**.
- Architecture: a module calling `HybridCache.RemoveByTagAsync` fails the build; `orvano migrate` starts no listener and its `ISignalConnectionState` reports false; verifies **AC-12**.
- Telemetry: the connected gauge reads 1, then 0 after the terminate; `cache.clears{reason=connect}` reads 2 after the first connect and one reconnect; `hb` is not in `signals.received`; verifies **AC-13**.
- Unknown commit is not counted: the unknown commit scenario above leaves `signals.sent` unchanged while the writer's local removal still runs; a confirmed commit adds 1 per kind; verifies **AC-6**, **AC-13**.
- Joined context: context B calls `UseTransaction` with context A's transaction; `Invalidate(B, …)` throws naming the context that began it, and `Invalidate(A, …)` then commits and sends; the existing retry on one connection test still passes (no joined flag on a begun transaction); verifies **AC-3**, **AC-4**.
- Boot announce: with the listener's database unreachable (and, separately, reachable), each observer sees `OnDisconnectedAsync` once and one `OnFallbackPollAsync` before the first connect attempt finishes, then `OnConnectedAsync` after a successful one; a failed first attempt adds no second `OnDisconnectedAsync`; verifies **AC-9**.
- Flap: on `ManualClock`, a connection terminated right after `LISTEN` makes the next attempt wait (n keeps growing up to the cap), and a connection that lived past `HeartbeatInterval` reconnects immediately; verifies **AC-9**.
- Hanging handler: a handler that never returns and ignores its token is cut off at `HandlerTimeout` with an Error log, and the next signal still reaches the other handlers; verifies **AC-10**.
- Dispatch lag: with a handler slower than `HandlerTimeout` per call and enough signals queued after the connect that the oldest waits past `HeartbeatTimeout`, `IsConnected` turns false, reads bypass the cache, and the listener reconnects; a stuck item from before that reconnect does not trip it again; verifies **AC-8**.
- Bad options: `ORVANO_SIGNALS__HANDLERTIMEOUT` above the heartbeat timeout stops startup naming the variable; verifies **AC-11**.
- Module isolation: the reflection test finds every public overload of each newly banned member in `BannedSymbols.Modules.txt`; the source scan test fails on a module file holding `pg_notify`; `SignalAwareHybridCache.InnerKey` is not a `string`; verifies **AC-12**.

## Job queue design (milestone 2)

Builds spec 0007 JOB-1 to JOB-6 on the signal machinery above. Rules here win where they add detail to JOB-1 to JOB-6; spec 0007 points back to them.

### Job queue scope and boundaries

- In: the SharedKernel job contracts, `JobsDbContext` and its first migration (`jobs.job`, `jobs.schedule`), enqueue in and out of a transaction, the runner (claim, lease, renewal, outcomes, backoff, dead jobs, shutdown), the `job` signal handler and connection observer, `JobOptions` with the half pool rule, schedules and their sync, the built in `jobs.cleanup` schedule, `CancelProjectJobsAsync`, the project and caller scope for project jobs, telemetry, the test driver, and the tests.
- Out (milestone 3, _Outbox design_): the outbox dispatcher. It needs `WorkerWake` (WAK-5), ENQ-1 on a platform context, and one more loop connection (OPL-1), nothing more from this section.
- Out (features 13, 14, 15, 29): every other job kind and schedule (project teardown and provisioning, signing key rotation, expired session cleanup, local file store temp cleanup). Each feature registers its own with JQ-5.
- Out (feature 46): an operator view of jobs, retrying a dead job, and toggling a schedule's `enabled` flag. Out (feature 23): per project fairness. There is no priority (JOB-2).

### Rules

**Contracts (JQ, `Orvano.SharedKernel/Jobs/`)**

- **JQ-1 (MUST)**: A job type is a record that implements `IJob`, which has one member, `static abstract string Kind { get; }`. The kind is the job's wire name: 3 to 100 characters matching `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$` (for example `jobs.cleanup`, `project.teardown`). Changing a payload in a way old rows cannot deserialize takes a new kind name (`auth.session_cleanup.v2`); old rows of the old kind drain or die (OUT-5). The payload holds ids and codes only, never personal values or secrets (spec 0011 CLS-2).
- **JQ-2 (MUST)**: `IJobHandler<in TJob> where TJob : IJob` has `Task HandleAsync(TJob job, JobContext context, CancellationToken cancellationToken)`. `JobContext` is a sealed record: `Guid Id`, `string Kind`, `int Attempt` (1 on the first run), `int MaxAttempts`, `Guid? ProjectId`, `DateTimeOffset RunAt`, `DateTimeOffset CreatedAt`. Handlers are idempotent (JOB-2): a job can run again after a crash, a lost lease, or an outcome write that failed. The token cancels on timeout (OUT-2), lease loss (CLM-5), and host shutdown (OUT-6).
- **JQ-3 (MUST)**: `IJobQueue` has three members, all `Task` returning with a required `CancellationToken` (spec 0002 ASY-2, ASY-4):
  - `Task<Guid?> EnqueueAsync<TJob>(DbContext context, TJob job, EnqueueOptions? options, CancellationToken cancellationToken) where TJob : IJob` joins `context`'s open transaction (ENQ-1);
  - `Task<Guid?> EnqueueAsync<TJob>(TJob job, EnqueueOptions? options, CancellationToken cancellationToken) where TJob : IJob` runs its own transaction (ENQ-6);
  - `Task<int> CancelProjectJobsAsync(Guid projectId, Guid? exceptJobId, CancellationToken cancellationToken)` (ENQ-7).
    `EnqueueOptions` is a sealed record with `init` properties `DateTimeOffset? RunAt` (null means now), `string? DedupeKey`, `Guid? ProjectId`.
- **JQ-4 (MUST)**: `PermanentJobFailureException(string message, Exception? inner = null)` is the one way a handler says "retrying will not help" (OUT-3). Any other exception is a failed attempt.
- **JQ-5 (MUST)**: `services.AddJobHandler<TJob, THandler>(JsonTypeInfo<TJob> jsonTypeInfo, Action<JobKindOptions>? configure = null) where TJob : IJob where THandler : class, IJobHandler<TJob>` registers `THandler` as a scoped `IJobHandler<TJob>` and a singleton `JobRegistration` (kind, job type, the `JsonTypeInfo` from the module's source generated `JsonSerializerContext`, spec 0002 JSN-1, the kind options, and a delegate that deserializes and calls the handler, so Infrastructure needs no reflection). `JobKindOptions` has `TimeSpan Lease` (default 5 minutes, 1 minute to 1 hour), `int MaxAttempts` (default 10, 1 to 100; 1 means at most one run only when nothing fails, since a lost claim acknowledgement can kill the job unrun, CLM-3), `TimeSpan Timeout` (default 1 hour, at least 1 second; a value above the longest timer delay, about 49.7 days, such as `TimeSpan.MaxValue`, means no deadline, OUT-2), and `bool RequiresProject` (default false; true makes ENQ-3 refuse a missing `ProjectId` and OUT-4 kill a row without one). `services.AddJobSchedule<TJob>(string name, string cron, TJob job) where TJob : IJob` registers a singleton `JobScheduleRegistration` (SCH-1); its payload is serialized later by `JobRegistry` with the kind's `JobRegistration`, so the order of the two calls does not matter. Both extensions check what they can alone (the kind and name patterns, the option ranges) and throw `ConfigurationException` (spec 0002 CFG-4), which `ServeCommand` already prints before exiting 1. Modules call both in `Add<Module>Module`, for every command. Both registration types are public sealed classes with internal constructors, read by Infrastructure.
- **JQ-6 (MUST)**: `JobAccessScope.Establish(IServiceProvider scopedServices, Guid? projectId)` (public static) sets the scope's `AccessContext` to `Caller.System` and the project, through the internal `AccessContext.Establish` (spec 0012 CLR-1: `system` is the caller for jobs). Only the runner calls it (CLM-7); `BannedSymbols.Modules.txt` bans the type, and the PRJ-3 architecture test allows it as the one setter outside the access layer (spec 0012 PRJ-3, amended).

**Tables (JDB, `Orvano.Infrastructure/Jobs/Data/`)**

- **JDB-1 (MUST)**: `JobsDbContext` (public sealed, so Host's `MigrationOrder` can name it) uses `UseOrvanoConventions("jobs", services)` on the shared platform `NpgsqlDataSource`, keeps its migrations in `Orvano.Infrastructure/Jobs/Data/Migrations` with history table `jobs.__ef_migrations_history`, has an `IDesignTimeDbContextFactory` (spec 0002 DAT-10), and is the first entry of `MigrationOrder` (spec 0011 MOD-2, spec 0007 INS-2). `AddInfrastructure` registers it with `AddDbContext` (scoped), so every command can enqueue and `/health/ready` sees its pending migrations.
- **JDB-2 (MUST)**: `jobs.job`, entity `Job : Entity` (queue row; changed only by the SQL in ENQ, CLM, and OUT, so neither `ITimestamped` nor `IVersioned`; the attempt fence in CLM-4 replaces `xmin`). Columns are in _Job tables_ below. Storage parameters `fillfactor = 70` and `autovacuum_vacuum_scale_factor = 0.05` through Npgsql's `HasStorageParameter` (JOB-1); `status` sits in the partial index predicates, so claims and outcomes are not HOT updates (every index gets a new entry), and the fillfactor helps less than it would otherwise. Indexes: `ux_job_dedupe_key` unique on `(kind, project_id, dedupe_key)` with `NULLS NOT DISTINCT`, partial `WHERE dedupe_key IS NOT NULL` (EF: `IsUnique().AreNullsDistinct(false).HasFilter("dedupe_key IS NOT NULL")`). A dedupe key is therefore scoped to its kind and its project: one module's key can never suppress another kind's job, and one project's key (which may come from that project's own input) can never suppress another project's. `NULLS NOT DISTINCT` makes two jobs with no project and the same kind and key collide (schedules, SCH-4), and the predicate keeps rows without a key out of the index, so they never collide; `ix_job_due` on `(run_at, id)` where `status = 'queued'`; `ix_job_lease` on `(locked_until, id)` where `status = 'running'` (expired leases and CLM-1's dead marking); `ix_job_finished` on `(finished_at)` where `status IN ('succeeded', 'dead')` for cleanup; `ix_job_project` on `(project_id)` where `project_id IS NOT NULL AND status IN ('queued', 'running')` for ENQ-7. Splitting due and running rows keeps an idle poll a short range scan however many future jobs wait. `project_id` is a plain uuid with no FK (spec 0011 REF-4).
- **JDB-3 (MUST)**: `jobs.schedule`, entity `JobSchedule : Entity, ITimestamped, IVersioned`. Columns are in _Job tables_ below: the table holds only what code cannot (the schedule's state), and each schedule's kind and payload come from its registration by name (SCH-2). Index `ux_schedule_name` unique on `name`; `ix_schedule_due` on `(next_run_at)` where `enabled`.
- **JDB-4 (MUST)**: CHECK constraints, each named per spec 0011 COL-7: `ck_job_status` (from `HasTextEnum<JobStatus>`, values `queued`, `running`, `succeeded`, `dead`), `ck_job_kind` (`char_length(kind) BETWEEN 3 AND 100`), `ck_job_attempt` (`attempt >= 0 AND attempt <= max_attempts`), `ck_job_max_attempts` (`max_attempts BETWEEN 1 AND 100`), `ck_job_dedupe_key` (`char_length(dedupe_key) BETWEEN 1 AND 200`), `ck_job_locked_by` (`char_length(locked_by) <= 100`), `ck_job_last_error` (`char_length(last_error) <= 2000`), `ck_job_trace_parent` (`char_length(trace_parent) <= 55`), `ck_job_lease` (`(status = 'running') = (locked_until IS NOT NULL AND locked_by IS NOT NULL)`), `ck_job_finished` (`(status IN ('succeeded', 'dead')) = (finished_at IS NOT NULL)`); `ck_schedule_name` (`char_length(name) BETWEEN 3 AND 100`), `ck_schedule_cron` (`char_length(cron) BETWEEN 9 AND 100`). The kind and name patterns are checked in code (JQ-1, SCH-1), not in SQL.

**Enqueue (ENQ)**

- **ENQ-1 (MUST)**: `EnqueueAsync` with a context checks everything first (ENQ-2, ENQ-3), then runs one `INSERT INTO jobs.job (…) VALUES (…, {payload}::jsonb, …) ON CONFLICT (kind, project_id, dedupe_key) WHERE dedupe_key IS NOT NULL DO NOTHING` (the arbiter is `ux_job_dedupe_key`, JDB-2) through `context.Database.ExecuteSqlAsync` (interpolated, so every value is a parameter; spec 0002 DAT-6; the payload is a text parameter cast to `jsonb`) on that context's connection and transaction. Rows affected 1 returns the new id; 0 returns `null` (a dedupe hit). The id is `Guid.CreateVersion7(now)`, `status` `queued`, `attempt` 0, `max_attempts` from the kind's options, `run_at` the option (normalized to UTC) or now, `created_at` now, `trace_parent` from `Activity.Current` when it is a W3C id, and the payload serialized with the registration's `JsonTypeInfo`. The caller's tracked entities are untouched; the row joins the transaction because the statement runs in it, so it commits or rolls back with the caller's change, and an execution strategy retry (SND-6) inserts it again in the new attempt only.
- **ENQ-2 (MUST)**: The context checks are SND-5's, through a new `TransactionSignals.EnsureEnlistable(DbContext)` (public static, same messages, already banned in modules by the type ban) called before the insert: an open transaction, a platform database context, not joined. A context with no transaction gets the SND-5 message, which names `InTransactionAsync`.
- **ENQ-3 (MUST)**: Argument checks, both overloads, before any I/O: the kind has a `JobRegistration` whose job type is `TJob` (else `InvalidOperationException` "No job handler is registered for kind '<kind>' (spec 0013 JQ-5)."); the serialized payload is at most 65,536 UTF-8 bytes; `DedupeKey`, when set, is 1 to 200 characters; `ProjectId`, when set, is not `Guid.Empty`, and is set when the kind has `RequiresProject` (each else `ArgumentException`).
- **ENQ-4 (MUST)**: When the insert affected a row and `run_at` is at or before now, the queue enlists `SignalKind.Job` with no values on the same context (through Infrastructure's `SignalBus`, so `signals.sent` counts it). SND-4 already makes it one `job` signal per transaction however many jobs it enqueues (SIG-3). A future job sends nothing; the poll finds it (WAK-2).
- **ENQ-5 (MUST)**: The `jobs.enqueued` count (JTL-1) is an on committed action (SND-1) per inserted row, so a rolled back or unknown commit enqueues nothing in the metric.
- **ENQ-6 (MUST)**: `EnqueueAsync` without a context creates a DI scope, resolves `JobsDbContext`, and runs ENQ-1 inside `InTransactionAsync` on it. Use it where no platform transaction is open: a handler queuing a follow up, startup work, or a request that writes nothing else. A caller that does have a transaction uses ENQ-1, so the job cannot outlive a rolled back change; the overload cannot see another context's open transaction, so this rule is documented (XML doc comment) and reviewed, not enforced.
- **ENQ-7 (MUST)**: `CancelProjectJobsAsync` runs one `UPDATE jobs.job SET status = 'dead', finished_at = @now, locked_until = NULL, locked_by = NULL, last_error = 'cancelled: project deleted' WHERE project_id = @project AND status IN ('queued', 'running') AND id IS DISTINCT FROM @except` in its own `InTransactionAsync` on `JobsDbContext` and returns the count. A running handler of such a job finds its lease lost at the next renewal (CLM-5). The project teardown job (feature 13, spec 0011 LIF-2 step 1) passes its own id as `exceptJobId`.

**Claim and lease (CLM, `Orvano.Infrastructure/Jobs/`)**

- **CLM-1 (MUST)**: `JobExecutor` (internal, registered by `AddInfrastructure`) has two operations, each one statement under the execution strategy in its own short transaction, so nothing else holds a row lock:
  1. The dead marking, `MarkExpiredDeadAsync`, runs on each poll tick (WAK-2 (2)), before the schedule tick, and once per `JobsDriver` pass (JTS-2); a signal, connect, or freed slot wake does not run it. It is bookkeeping only: the claim never takes a row on its last attempt, so a dead marking that waits for the poll changes nothing but when `finished_at` is set (at most `PollInterval` later). `UPDATE jobs.job SET status = 'dead', finished_at = @now, locked_until = NULL, locked_by = NULL, last_error = 'lease expired on the last attempt' WHERE id IN (SELECT id FROM jobs.job WHERE status = 'running' AND locked_until < @now AND attempt >= max_attempts FOR UPDATE SKIP LOCKED) RETURNING id, kind, attempt` (each returned row is counted and logged as dead on commit, OUT-4).
  2. The claim, `ClaimAsync`, runs on every wake: due rows first and expired leases only when slots remain, each through its own index (JDB-2). PostgreSQL refuses `FOR UPDATE` in a `UNION` branch, even a parenthesized one (`0A000`), so each branch locks inside a derived table of its own:

     ```sql
     UPDATE jobs.job AS j
     SET status = 'running', attempt = j.attempt + 1, locked_by = @worker,
         locked_until = @now + COALESCE(
           (SELECT k.lease FROM unnest(@kinds::text[], @leases::interval[]) AS k(kind, lease) WHERE k.kind = j.kind),
           interval '5 minutes')
     FROM (
       SELECT id FROM (
         SELECT id FROM (
           SELECT id FROM jobs.job WHERE status = 'queued' AND run_at <= @now AND id <> ALL(@mine)
           ORDER BY run_at, id LIMIT @free FOR UPDATE SKIP LOCKED) AS due
         UNION ALL
         SELECT id FROM (
           SELECT id FROM jobs.job WHERE status = 'running' AND locked_until < @now AND attempt < max_attempts AND id <> ALL(@mine)
           ORDER BY locked_until, id LIMIT @free FOR UPDATE SKIP LOCKED) AS expired
       ) AS both_sets LIMIT @free
     ) AS pick
     WHERE j.id = pick.id
     RETURNING j.id, j.kind, j.payload::text, j.project_id, j.attempt, j.max_attempts, j.run_at, j.created_at, j.trace_parent
     ```

  `@kinds` and `@leases` are the registered kinds and their `Lease`; an unregistered kind gets 5 minutes. `@mine` is the ids this process is still running (CLM-2). Taking due rows first means crash recovery waits only while the queue is saturated; the expired set is usually empty. When the due branch fills the outer `LIMIT`, the append never runs the expired branch, so it locks nothing; a row the second branch locks but the outer `LIMIT` drops stays as it was. The verify run of 2026-10-19 checked this form against the intent on the live schema (order, `@mine`, the last attempt skip, the limits).

- **CLM-2 (MUST)**: `@free` is `Concurrency` minus the handlers this process has not seen return, including timed out ones (OUT-2) and ones whose lease was lost (CLM-5); with no free slot there is no claim. Their job ids form the in process running set passed as `@mine`, so this process never runs the same job twice at once. Each claimed job runs on its own task, so at most `Concurrency` handlers run per process. `@worker` (`locked_by`) is the machine name cut to 80 characters, `:`, and the process instance id (the 8 hex characters of LSN-1, moved from Host's `SignalInstance` to an Infrastructure `OrvanoInstance` singleton that both the listener's application name and the runner read). The instance id must be new for every process start, never stable or configured, because the fence (CLM-4) relies on it.
- **CLM-3 (MUST)**: A claim whose commit outcome is unknown leaves its rows `running` under this worker, with no task running them; their lease expires and they are claimed again, costing one attempt. This is the accepted price of at least once delivery.
- **CLM-4 (MUST)**: Every statement that touches a claimed row after the claim (renewal, outcome) is fenced: `WHERE id = @id AND status = 'running' AND locked_by = @worker AND attempt = @attempt`. A fenced statement that affects no row means another worker claimed the job after this lease expired, or ENQ-7 cancelled it: the lease is lost.
- **CLM-5 (MUST)**: Renewal runs every lease ÷ 3 (a `TimeProvider` timer per running job) as `UPDATE … SET locked_until = @now + @lease` with the CLM-4 fence. Each job has at most one renewal in flight; a tick that finds one still running is skipped. A renewal is a single attempt with no execution strategy retry (a `JobsDbContext` built with `EnableRetryOnFailure(0)` through the `UseOrvanoConventions` npgsql callback) and a command timeout of lease ÷ 3, because a retrying renewal can outlive the lease it is renewing. A lost lease cancels the handler's token at once, logs a Warning, writes no outcome, and frees the slot only when the handler returns. A renewal that throws is retried at the next tick; when the clock passes the last `locked_until` this worker set without a successful renewal, the runner treats the lease as lost too (if that renewal did commit, the job waits out the lease and costs an attempt, like CLM-3). When the handler returns, the runner stops its renewal timer and awaits any renewal in flight before writing the outcome; a renewal that finds no row after the handler returned is ignored.
- **CLM-6 (MUST)**: The lease is the only crash detector. A worker that dies leaves `running` rows that any worker claims once `locked_until` passes; the claim counts an attempt, so a job that keeps killing its worker reaches `max_attempts` and dies through CLM-1's dead marking (JOB-3).
- **CLM-7 (MUST)**: Each attempt runs in a new async DI scope: `JobAccessScope.Establish(scope, job.ProjectId)` first (JQ-6), then the registration's delegate deserializes the payload and calls `HandleAsync` with a token linked to the runner's stopping token, the lease loss token, and a `CancellationTokenSource(Timeout, timeProvider)` (spec 0002 ASY-7).
- **CLM-8 (SHOULD)**: Time is the app's clock (AC-29). Lease expiry compares one host's clock with another's, so replica clocks should be within a few seconds (NTP). The 1 minute minimum lease (JQ-5) leaves 40 seconds between the last renewal and expiry for a stall or skew; a smaller skew only shifts when a crashed worker's job is picked up.

**Outcomes and dead jobs (OUT)**

- **OUT-1 (MUST)**: The handler returns: one fenced `UPDATE` sets `status = 'succeeded'`, `finished_at = @now`, lease columns null (`last_error` keeps the last failure, if any, for operators).
- **OUT-2 (MUST)**: A failed attempt: the handler throws (anything but JQ-4 and a cancellation OUT-8 classes otherwise), its `Timeout` passes, its kind has no registered handler (`last_error` `no handler registered for kind`), or its payload does not deserialize (`payload could not be read: <JsonException message>`). If `attempt < max_attempts`, a fenced `UPDATE` sets `status = 'queued'`, `run_at = @now + delay`, lease columns null, and `last_error`; else OUT-4. Treating an unknown kind or payload as an ordinary failure lets a rollback to the older version drain those rows before they die. On timeout the runner cancels the token and writes the outcome at once, so the retry schedule starts, but keeps the slot and the id in the running set (CLM-2) until the handler returns, logging a Warning each lease period it has not; its late exception is logged at Debug. A handler that never returns holds its slot until the process restarts. `last_error` for a timeout is `timed out after <Timeout>`. The timeout runs on a `TimeProvider` timer; a `Timeout` above the longest timer delay (`JobExecutor.MaxTimerDelay`, about 49.7 days) sets no deadline instead of throwing (JQ-5). Any exception around the handler (a payload reader that throws something other than `JsonException`, a scope that fails to build) is a failed attempt, and the slot is freed in a `finally` unless an abandoned handler still holds it, so no early exception can leak a slot.
- **OUT-3 (MUST)**: Backoff (JOB-3): d = min(1 hour, 10 s × 2^(attempt − 1)) and delay = d / 2 + random × d / 2, with `random` from `JobBackoff.NextRandom()` = `RandomNumberGenerator.GetInt32(int.MaxValue) / (double)int.MaxValue`, uniform over [0, 1) ("equal jitter", so a retry never comes sooner than half the curve). `System.Random` is banned repo wide (`BannedSymbols.txt`, spec 0006 TOK-1), so the source is the CSPRNG; one call per failed attempt costs nothing at retry rates, and `Delay` clamps its input to [0, 1]. `JobBackoff.Delay(int attempt, double random)` is a pure internal function, computed in `double` with the exponent clamped so attempt 100 cannot overflow, and unit tested at its bounds; the base, cap, and curve are constants, not options.
- **OUT-4 (MUST)**: Dead: a fenced `UPDATE` sets `status = 'dead'`, `finished_at = @now`, lease columns null, and `last_error`. Reached at `max_attempts` (OUT-2), by `PermanentJobFailureException`, by a kind with `RequiresProject` whose row has no `project_id` (`project id missing`), by a lease that expired on the last attempt (CLM-1), or by ENQ-7. A dead job is logged at Error and counted (JTL-1), stays visible for 30 days (SCH-7), and keeps its dedupe key until then. Nothing in this milestone revives it (feature 46).
- **OUT-5 (MUST)**: `last_error` is the exception's type name, `: `, and its message, cut to 2000 characters; the full exception goes to the log. It may quote input, so it is marked `DataClass.Personal`.
- **OUT-6 (MUST)**: Host shutdown, in this order: the runner stops its wake loop, awaits a claim or schedule tick in flight (so no row is left claimed with no task), then cancels every running handler's token. A claim is bounded by `JobExecutor.ClaimBound` (10 s, both statements and their retries, a `CancellationTokenSource(ClaimBound, timeProvider)`), so a stalled database cannot hold the loop or the shutdown behind it; a claim cut off leaves any row it took to its lease (CLM-3), and the loop logs it and waits for the next wake (WAK-4). Each handler whose cancellation OUT-8 classes as shutdown gets a fenced release: `status = 'queued'`, `attempt = attempt - 1`, `run_at = @now`, lease columns null, plus a `job` signal (the release runs in `InTransactionAsync` on `JobsDbContext`), so a deploy costs no attempt. A handler that finishes during shutdown writes its normal outcome. The runner waits for handlers until the host's shutdown timeout, which `ServeCommand` sets to 25 seconds (`HostOptions.ShutdownTimeout`); the reference compose file sets `stop_grace_period: 35s` on the Orvano service so the container is not killed first. Anything still running then is recovered by its lease (CLM-6).
- **OUT-7 (MUST)**: An outcome write that fails after the execution strategy's retries is logged at Error; the job is recovered by its lease (CLM-6). The attempt returns `write_failed` (`JobOutcome.WriteFailed`) to the runner and `JobsDriver`, is counted in no `jobs.attempts` outcome (the intended outcome did not happen), and a failed release is not counted as released. A fenced write whose first try committed but reported failure finds no row on the retry and is logged as a lost lease; that misreport is harmless.
- **OUT-8 (MUST)**: Cancellation cause and write tokens. The handler's token links three causes; when a handler ends with `OperationCanceledException` the runner checks, in order: lease lost (CLM-5) → write nothing; timed out → failed attempt (OUT-2); the stopping token is cancelled → release (OUT-6); otherwise (the handler's own cancellation, such as an `HttpClient` timeout) → failed attempt. Outcome and release writes, and the signal they enlist, never use the stopping token: they run with a 10 second `CancellationTokenSource(TimeSpan.FromSeconds(10), timeProvider)` (spec 0002 ASY-7), the same bound as `HandlerTimeout`. Renewals use their own lease ÷ 3 bound (CLM-5).

**Wake and poll (WAK)**

- **WAK-1 (MUST)**: `JobRunner` (internal `BackgroundService`, worker role only, JOP-3) loops on one wake: a `Channel<bool>` with capacity 1 and `DropWrite`, so any number of wakes between two claims coalesce into one. On each wake it runs `JobExecutor`'s claim (CLM-1) and starts what it claimed.
- **WAK-2 (MUST)**: Wake sources: (1) the `job` signal handler (`ISignalHandler` for `SignalKind.Job`, which only writes to the channel, HND-4); (2) a `PeriodicTimer` on `TimeProvider` every `PollInterval`, always on, connected or not, which also runs CLM-1's dead marking and then the schedule tick (SCH-4) before its claim (each in its own try and catch, SCH-3), and is the only path for future `run_at` and retry backoff (no signal is sent for them, ENQ-4); (3) the runner's `ISignalConnectionObserver.OnConnectedAsync` (HND-3: signals sent during the gap are lost); (4) a job finishing while the most recent claim returned as many rows as it asked for (more may be due), which writes a wake.
- **WAK-3 (MUST)**: The observer adds no fallback poll of its own: the always on poll (WAK-2 (2)) is already the fallback, so `OnDisconnectedAsync` and `OnFallbackPollAsync` keep their empty defaults.
- **WAK-4 (MUST)**: A claim that throws logs an Error and waits for the next wake (at most `PollInterval`); the loop never ends while the host runs.
- **WAK-5 (MUST)**: Milestone 3's hook: `WorkerWake` (internal singleton) lets another worker loop subscribe to the same wakes (signal, poll, connect), so the outbox dispatcher (EVT-3) needs no listener code of its own. It is built now with the runner as its first subscriber.

**Schedules (SCH)**

- **SCH-1 (MUST)**: `AddJobSchedule` names are 3 to 100 characters matching JQ-1's pattern (for example `jobs.cleanup`), checked at registration (JQ-5). Cron is `Cronos` `CronFormat.Standard` (five fields, minute first, which also accepts `L`, `W`, `#`, and names), evaluated in UTC. `JobRegistry` (internal singleton, built from every `JobRegistration` and `JobScheduleRegistration`) checks each cron with `CronExpression.Parse` and requires a next occurrence from now (an expression such as `0 0 30 2 *` parses but never fires), and rejects a duplicate kind or schedule name, a schedule whose kind has no handler or has `RequiresProject` (schedules have no project, SCH-6), and a schedule payload that serializes, with the kind's `JsonTypeInfo`, to more than 65,536 bytes, so ENQ-3 can never throw at tick time. `StartupChecks` builds it in every `serve` role and turns its errors into `StartupFailedException` naming the schedule or kind; `ServeCommand` registers `AddJobRunner` after `StartupChecks`, and the runner resolves the same registry, so a bad registration stops startup in every role with a message, not a stack trace.
- **SCH-2 (MUST)**: Code is the source for each schedule's `cron`, kind, and payload; the table holds `cron` (only to notice a change), `enabled`, `next_run_at`, and `last_fired_at`. At worker start, before its first claim, the runner syncs in one `InTransactionAsync` on `JobsDbContext`: an upsert per registered schedule, in name order so concurrent syncs take row locks in the same order (`INSERT … ON CONFLICT (name) DO UPDATE SET cron, next_run_at, updated_at` only when the cron differs, recomputing `next_run_at` from now; a new row gets `enabled = true` and the next occurrence after now), then `DELETE` of rows whose name is not registered. Concurrent syncs from several workers converge (same input, same lock order). Two code versions running at once would undo each other's crons and deletions; RUN-7 stops every replica on upgrade, so this happens only on a mixed fleet run by hand.
- **SCH-3 (MUST)**: A sync that fails is logged at Error and retried on the next poll tick; the runner claims jobs meanwhile but fires no schedule until a sync succeeds. A schedule tick that fails is logged at Error and does not stop the claim that follows it on the same poll (WAK-2).
- **SCH-4 (MUST)**: The schedule tick (every poll, WAK-2) runs in one `InTransactionAsync` on `JobsDbContext`: `SELECT id, name, next_run_at FROM jobs.schedule WHERE enabled AND next_run_at <= @now ORDER BY next_run_at LIMIT 100 FOR UPDATE SKIP LOCKED`; for each row, the kind and payload come from `JobRegistry` by name (a row whose name is not registered is skipped; the next sync deletes it), then ENQ-1 on that context with `dedupe_key = '<name>:<next_run_at as yyyyMMddTHHmmssZ>'` and `run_at = next_run_at`, then `next_run_at = <next occurrence strictly after @now>`, `last_fired_at = @now`, `updated_at = @now`. A null next occurrence cannot happen for a cron SCH-1 accepted; if it does, the tick logs an Error and sets `enabled = false` for that row. The row lock makes one worker fire a given occurrence; the dedupe key makes a second fire of the same occurrence (after a lost commit, or a lock released by a crash) a no op, so each occurrence fires exactly once (JOB-5).
- **SCH-5 (MUST)**: Missed occurrences collapse: a schedule that is days behind fires once, for its stored `next_run_at`, and then jumps to the next occurrence after now. A disabled schedule never fires; when feature 46 turns one back on it fires once if `next_run_at` passed, then continues. Schedules fire on the poll, so up to `PollInterval` late (5 minutes at the largest setting); `run_at` keeps the planned time, so `jobs.lag` shows it.
- **SCH-6 (MUST)**: Schedules are instance wide: their jobs have no `project_id`. Their kinds follow JQ-1, and their handlers are idempotent like any other.
- **SCH-7 (MUST)**: The built in `jobs.cleanup` schedule (cron `17 3 * * *`, kind `jobs.cleanup`, payload `{}`) and its handler, registered by `AddInfrastructure` with default kind options except `MaxAttempts` 3, its JSON type info from an `InfrastructureJsonContext`: `DELETE FROM jobs.job WHERE id IN (SELECT id FROM jobs.job WHERE status = 'succeeded' AND finished_at < @now - 7 days LIMIT 5000)`, repeated until it deletes fewer than 5000, then the same for `dead` older than 30 days. Retentions are constants (JOB-3).

**Options (JOP)**

- **JOP-1 (MUST)**: `JobOptions` in `Orvano.Infrastructure/Jobs/` (`Section = "Jobs"`): `TimeSpan PollInterval` (default 5 s) and `int? Concurrency` (default null), each with an XML doc comment (CFG-1). A source generated validator requires `PollInterval` between 1 second and 5 minutes and an explicit `Concurrency` between 1 and 256.
- **JOP-2 (MUST)**: The pool rule (JOB-4, PG-4) lives in `Orvano.Host`, which owns `DatabaseOptions` (CFG-5). Its limit is `PoolSize` / 2 − 2 (integer division): half the pool, less the one connection each worker loop uses, the runner's and the outbox dispatcher's (JOP-4, OPL-1). A `PostConfigure<JobOptions>` fills a null `Concurrency` with max(1, min(processor count × 2, 16, `PoolSize` / 2 − 2)), and an `IValidateOptions<JobOptions>` fails an explicit value above the limit with "ORVANO_JOBS__CONCURRENCY (<n>) must be at most <limit>: half of ORVANO_DATABASE__POOLSIZE (<pool>) less two connections for the job runner and the outbox dispatcher (spec 0007 JOB-4)." `DatabaseOptions.PoolSize` is `[Range(6, 1000)]`, so the limit is at least 1 and the default can never fail startup (spec 0007 JOB-4, amended: at the default pool of 30 the default is at most 13). Milestone 2 built `PoolSize` / 2 − 1 with a pool of at least 4; milestone 3 lowers it (OPL-1, build plan step 26).
- **JOP-3 (MUST)**: `AddJobRunner()` registers `JobRunner`, its `job` signal handler, its connection observer, and `WorkerWake`; `ServeCommand` calls it only when `ServerRoles.Worker` is true. `AddInfrastructure` registers `JobsDbContext`, `IJobQueue`, `JobExecutor`, `JobRegistry`, `JobOptions`, and the `jobs.cleanup` handler and schedule for every command. An `api` only process enqueues and sends `job` signals but never claims.
- **JOP-4 (MUST)**: Platform pool use, counted per worker process: each running handler holds at most one platform connection (below); its renewal takes one more for milliseconds while the handler runs; its outcome or release write takes one after the handler's scope is disposed, never alongside the renewal (CLM-5), so each job uses at most 2 at once. The runner's loop uses 1 more, serially, for the dead marking, the schedule sync and tick, and the claim, and the outbox dispatcher's loop 1 more, serially, for its batches (OPL-1). The signal listener is not counted: it uses its own unpooled `"signals"` data source (LSN-1), already in PG-4's `max_connections` sum. So in the steady state (handlers only, plus the two loops) jobs use at most `Concurrency` + 2 ≤ `PoolSize` / 2, leaving half the pool for requests (PG-4), and in the worst case (every handler holding a connection while every renewal fires) at most 2 × `Concurrency` + 2 ≤ `PoolSize` − 2, so the workers can never take the whole pool and a request always gets a connection. Renewals are not given their own half: they are rare (every lease ÷ 3) and short, and reserving for them would halve throughput for a case that already leaves requests a connection. The rule assumes a handler holds at most one platform connection at a time (one context in use at once); a handler that needs two at once says so in a comment and is reviewed against the pool. Handlers that open project databases use the project cap as usual.

**Telemetry (JTL)**

- **JTL-1 (MUST)**: Metrics on `InfrastructureTelemetry` (meter `Orvano.Infrastructure`, spec 0002 LOG-5): `orvano.infrastructure.jobs.enqueued` (counter, `{job}`, tag `kind`; confirmed commits of inserted rows only, ENQ-5); `orvano.infrastructure.jobs.attempts` (counter, tags `kind` and `outcome`: `succeeded`, `failed` (will retry), `dead`, `released`, `lease_lost`; `write_failed` is never a tag value, OUT-7); `orvano.infrastructure.jobs.duration` (histogram, `s`, tags `kind` and `outcome`, from handler start to outcome); `orvano.infrastructure.jobs.lag` (histogram, `s`, tag `kind`, claim time minus `run_at`), both histograms with the explicit bucket boundaries 0.01, 0.05, 0.1, 0.5, 1, 5, 30, 60, 300, 1800, and 3600 seconds through the instrument advice API (the default boundaries suit milliseconds); `orvano.infrastructure.jobs.running` (observable gauge, this process's running handlers); `orvano.infrastructure.jobs.schedules.fired` (counter, tag `schedule`, counted on confirmed commit when the enqueue inserted a row). Kinds and schedule names come from code, so the tags stay low in cardinality: a claimed row whose kind is not registered is tagged `unknown`, never with the kind text read from the database. No job, project, or user id tags.
- **JTL-2 (MUST)**: Logs on `InfrastructureLog`, event ids `LogEventIds.Infrastructure + 100` to `+ 199`: runner started (Information: concurrency, poll interval, worker id); claim failed (Error); attempt started and succeeded (Debug: kind, id, attempt); attempt failed (Warning: kind, id, attempt of max, next `run_at`, exception); job dead (Error: kind, id, attempt, reason, exception when there is one); lease lost (Warning); timed out and abandoned (Warning, then Debug for the late exception); released at shutdown (Information: count); outcome write failed (Error); schedule sync (Information: added, updated, removed counts) and sync failed (Error); schedule fired (Debug: name, fire time); cleanup (Information: deleted counts); a cancellation callback that threw (Warning, `+ 120`: lease loss, the timeout, and the handler's re-cancel go through `CancelAsync`, observed, outside the renewal lock, so a throwing handler callback never reaches a timer thread). Payloads and dedupe keys only at Debug (they may hold user ids, spec 0006 LOG-2).
- **JTL-3 (MUST)**: Each attempt runs in an activity on the `Orvano.Infrastructure` source, named `job <kind>`, kind `Consumer`, linked to the row's `trace_parent` when present, with tags `orvano.job.kind`, `orvano.job.id`, and `orvano.job.attempt` (traces may carry ids; metrics may not). An exception sets the activity status to error.

**Testing time (JTS)**

- **JTS-1 (MUST)**: Every time in this section comes from the injected `TimeProvider` (spec 0002 GEN-9, ASY-7): `@now` and every computed time are SQL parameters, and no statement calls `now()`, `clock_timestamp()`, or `CURRENT_TIMESTAMP`. Timers (`PeriodicTimer` for the poll, renewal timers, the timeout source) are built on the same `TimeProvider`, and cron occurrences are computed from it.
- **JTS-2 (MUST)**: `Orvano.Testing` gains `JobsDriver` (reaching `JobExecutor` through `InternalsVisibleTo`, which `Orvano.Infrastructure.csproj` adds for `Orvano.Testing`): `RunDueAsync(IServiceProvider services, CancellationToken cancellationToken)` runs the schedule sync (SCH-2, idempotent), CLM-1's dead marking, the schedule tick, then claims and runs every due job on the current clock inline (no background loop), repeating until a claim returns nothing, and returns each attempt's kind, id, and outcome. It throws `InvalidOperationException` naming the kinds it saw after 1000 attempts in one call, so a handler that keeps enqueuing due follow ups fails the test instead of hanging it. Module tests host with `ORVANO_ROLES=api` (no runner), advance the clock, and call it. The integration tests' `ManualClock` moves to `Orvano.Testing` so module tests share it.
- **JTS-3 (MUST)**: Runner tests that need the real loop (signal wake, two workers, shutdown) use `OrvanoApiFactory` hosts with role `worker` and short `PollInterval`, and pin their claims with `JobsDriver` or by advancing `ManualClock`, never with sleeps longer than the wake bound they assert.
- **JTS-4 (MUST)**: Module isolation: `BannedSymbols.Modules.txt` adds `T:Orvano.SharedKernel.Jobs.JobAccessScope` (JQ-6); the CAC-5 module source scan also fails on `jobs.job` and `jobs.schedule` (case insensitive), since a module writing the queue directly would skip ENQ-3 and ENQ-4. An architecture test pins `JobAccessScope.Establish`'s only caller to `JobExecutor` (JQ-6).

### Job state transitions

`queued` → (claim, CLM-1) `running` → one of: `succeeded` (OUT-1); `queued` with a later `run_at` (OUT-2); `queued` due now with `attempt` restored (OUT-6); `dead` (OUT-4). `running` with an expired lease → `running` under another worker (CLM-6) or `dead` on its last attempt (CLM-1). `queued` or `running` → `dead` by ENQ-7. `succeeded` and `dead` are final; cleanup deletes them (SCH-7). Every transition from `running` is fenced on worker and attempt (CLM-4).

Runner: `Starting` (sync schedules, SCH-2) → `Running` (wake loop) → `Stopping` (no claims, cancel, release, OUT-6) → `Stopped`.

| Shutdown                   | budget                               | `HostOptions.ShutdownTimeout` 25 s in `ServeCommand`; compose `stop_grace_period: 35s` (OUT-6)                              |
| Histograms                 | bucket boundaries                    | 0.01 to 3600 s, fixed list in JTL-1                                                                                         |
| Project required           | per kind                             | `JobKindOptions.RequiresProject` (JQ-5, ENQ-3, OUT-4)                                                                       |
| Cleanup                    | retentions, chunk                    | constants 7 days, 30 days, 5000 (SCH-7)                                                                                     |
| Telemetry                  | meter, activity source, event ids    | `Orvano.Infrastructure`; `LogEventIds.Infrastructure + 100` to `+ 199` (JTL-1 to JTL-3)                                     |
| Clock                      | now, timers                          | injected `TimeProvider` (JTS-1)                                                                                             |

### Job queue invariants

- A job row exists only if the transaction that enqueued it committed; a `job` signal goes out only for a committed, due job.
- At most one worker holds a job's lease, and only the holder of the current attempt can change the row.
- A dedupe key is taken, within its kind and project, until the row is deleted, across every status, so a schedule occurrence fires once and no kind or project can suppress another's job.
- No job runs past `max_attempts`; every failure path ends in `queued` with a later `run_at`, or `dead`.
- Every time the queue stores or compares comes from the app's `TimeProvider`.

### Job queue security model

No caller facing surface in this milestone. Jobs run as `Caller.System` (spec 0012 CLR-1) with the row's project, which only the enqueuing code chose, so a job can never act for another project than the one its code named; modules cannot set that scope themselves (JQ-6, JTS-4). Payloads hold ids and codes (spec 0011 CLS-2) and are marked `Personal`, like `last_error` and `dedupe_key`, so feature 49 and LOG-3 treat them that way; their retention is 7 or 30 days. Any session with the platform owner role can insert jobs directly (PG-2a); that role already owns every platform table.

### Job queue configuration required

- `ORVANO_JOBS__POLLINTERVAL` (5 s, 1 s to 5 minutes): how often a worker polls for due jobs and fires schedules
- Not a variable: `serve` sets the host shutdown timeout to 25 seconds, and the reference compose file gives the Orvano service `stop_grace_period: 35s`, so a deploy releases running jobs instead of killing them (OUT-6). Schedules fire up to `PollInterval` late (SCH-5).
- `ORVANO_JOBS__CONCURRENCY` (smallest of processor count × 2, 16, and half of `ORVANO_DATABASE__POOLSIZE` less two): jobs one worker process runs at once; at most half the platform pool less two (13 at the default pool of 30; milestone 3, OPL-1)
- `ORVANO_DATABASE__POOLSIZE` (30, now at least 6): the platform pool, which the job runner's limit is derived from (JOP-2)

- Schedules: a bad name stops startup with a `ConfigurationException` message; a bad cron, a cron with no next occurrence (`0 0 30 2 *`), a duplicate, an unknown kind, and a 70 KB payload each stop startup with a `StartupFailedException` message naming the schedule and exit code 1; two workers tick at the same `ManualClock` instant and one job exists with the expected dedupe key; a 3 day gap fires once; a cron change moves `next_run_at`; a removed registration deletes its row; a disabled row stays unfired; a tick made to throw is logged and the claim on the same poll still runs; `JobsDriver.RunDueAsync` on an `api` host fires a due schedule (it syncs first); verifies **AC-24**, **AC-29**.

## Outbox design (milestone 3)

Builds spec 0007 EVT-1 to EVT-3 on the job queue above, and names what EVT-4's readers will need. Rules here win where they add detail to EVT-1 to EVT-3; spec 0007 points back to them. A module announces an event by adding it to its own `<module>.outbox` table in the same `SaveChanges` and transaction as the change; a worker loop (the dispatcher) moves each committed event into one job per subscriber, and the job runner delivers those jobs with its usual leases, retries, and dead marking.

### Outbox scope and boundaries

- In: the SharedKernel outbox contracts and registrations, the shared EF configuration (`HasOutbox`), publishing inside the caller's transaction, `OutboxRegistry` and its startup checks, the dispatcher loop on `WorkerWake`, the subscriber job kind and its payload, the `outbox.cleanup` schedule, the pool limit change (JOP-2), telemetry, the guard rails, the test driver, and the tests. The first real outbox comes with the first module that announces something (features 13 and 14); this milestone proves the path with a test module's outbox.
- Out (features 33 to 36, EVT-4): realtime, platform events, and webhooks. What they need from this section is listed in _What EVT-4's readers will need_ below; none of it is built here.
- Out (feature 34): events caused by writes to project databases (spec 0007 EVT-1). Outboxes live in the platform database only.
- Out (feature 46): an operator view of outboxes and of dead deliveries; a dead delivery is a dead job, retried the way feature 46 retries any job.

### Rules

**Contracts (OBX, `Orvano.SharedKernel/Outbox/`)**

- **OBX-1 (MUST)**: An event type is a public sealed record in the publishing module's `Contracts/` that implements `IOutboxEvent`, which has one member, `static abstract string Type { get; }`. The type is the event's wire name: 3 to 100 characters matching `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+\.v[1-9][0-9]*$` (at least one name segment between the schema and the version), whose first segment is the publishing module's schema (`auth.user.created.v1`, spec 0007 EVT-2). A change old rows or old subscribers cannot read takes a new version (`auth.user.created.v2`); the publisher may publish both while subscribers move. The record holds ids and codes only, never personal values or secrets (spec 0011 CLS-2).
- **OBX-2 (MUST)**: `IOutbox` has one member, `Guid Publish<TEvent>(DbContext context, TEvent @event, Guid? projectId) where TEvent : IOutboxEvent`. It is synchronous and does no I/O: it adds the event to `context`'s change tracker (PUB-1), so the caller's next `SaveChangesAsync` writes it with the change. It returns the event's id. `projectId` is the project the event is about, or null for an instance wide event; it becomes the delivery job's project (DLV-3), so a subscriber runs in that project's scope.
- **OBX-3 (MUST)**: `services.AddOutbox(string schema, Action<OutboxBuilder> configure)` registers the module's outbox, called once in `Add<Module>Module` for every command. `OutboxBuilder.Event<TEvent>(JsonTypeInfo<TEvent> jsonTypeInfo) where TEvent : IOutboxEvent` (returns the builder) adds one event type with the JSON type info from the module's source generated `JsonSerializerContext` (spec 0002 JSN-1). The extension checks what it can alone and throws `ConfigurationException` (spec 0002 CFG-4): the schema matches `^[a-z][a-z0-9_]{1,30}$`; each type matches OBX-1 and its first segment equals `schema`; no type is added twice. It registers a singleton `OutboxRegistration` (schema and its events, each an `OutboxEventRegistration`: type name, CLR type, `JsonTypeInfo`). Both are public sealed classes with internal constructors, read by Infrastructure and by EVT-4's readers.
- **OBX-4 (MUST)**: A subscriber implements `IEventHandler<in TEvent> where TEvent : IOutboxEvent` in its own module: `Task HandleAsync(TEvent @event, EventContext context, CancellationToken cancellationToken)`. `EventContext` is a sealed record: `Guid EventId`, `string Type`, `DateTimeOffset OccurredAt`, `Guid? ProjectId`, `JobContext Job` (the delivery job's attempt and ids, JQ-2). Handlers are idempotent (spec 0007 EVT-3): an event can reach a subscriber more than once. The token cancels as a job handler's does (JQ-2).
- **OBX-5 (MUST)**: `services.AddEventHandler<TEvent, THandler>(string name, Action<JobKindOptions>? configure = null) where TEvent : IOutboxEvent where THandler : class, IEventHandler<TEvent>` registers `THandler` as a scoped `IEventHandler<TEvent>`, a singleton `EventSubscription` (name, the event's type name and CLR type), and a `JobRegistration` whose kind is `name` (DLV-1). `name` is the subscriber's stable identity: it is the delivery job's kind, part of every delivery's dedupe key, and the metric tag, so renaming it is a new subscriber (rows of the old kind drain or die, OUT-2). It follows JQ-1's pattern and should start with the subscribing module's name and say what it does (`platform.user_created.count_users`). The extension throws `ConfigurationException` for a bad name or out of range options (JQ-5's checks) and for `RequiresProject = true`: a subscriber reads the project from `EventContext.ProjectId`, and an instance wide event must not die at once (OUT-4). A module may subscribe to its own events and to any module's events whose records it can reference through that module's `Contracts` (spec 0002 LAY-4).
- **OBX-6 (MUST)**: `IOutboxRegistry` (public, implemented by Infrastructure's `OutboxRegistry` singleton) is the read only view of every registration: `IReadOnlyList<OutboxRegistration> Outboxes` (in schema order, ordinal), `OutboxEventRegistration? FindEvent(string type)`, and `IReadOnlyList<EventSubscription> SubscribersOf(string type)` (in name order, ordinal). The dispatcher, the cleanup, the delivery job, and EVT-4's readers read it; nothing writes it after startup. It replaces spec 0007 EVT-1's "registers its schema with `IOutboxRegistry`": registration is `AddOutbox` (OBX-3), and the registry is what reads the result.
- **OBX-7 (MUST)**: `OutboxRegistry` checks what single registrations cannot, and `StartupChecks` turns its `Problems` into one `StartupFailedException` in every `serve` role, next to `JobRegistry`'s (SCH-1): a schema registered twice, an event type registered by two outboxes, and a subscriber whose event type no outbox registers, or whose CLR type differs from the registered one. A subscriber name that equals another job kind or subscriber is already `JobRegistry`'s duplicate kind problem. So a bad registration stops startup with a message naming it and exit code 1.

**Table (OTB)**

- **OTB-1 (MUST)**: `OutboxEvent : Entity` (public sealed, in `Orvano.SharedKernel/Outbox/`) is the row: `Type`, `Payload` (JSON text mapped to `jsonb`), `ProjectId`, `OccurredAt`, `DispatchedAt`, `TraceParent`, each text column marked `[DataClass]` (spec 0011 CLS-1). It is changed only by PUB-1's insert and the SQL in DSP and OCL, so, like `Job`, it is neither `ITimestamped` nor `IVersioned`; its `ProjectId` is a nullable plain id on a history row (spec 0011 REF-4), so it is not `IProjectScoped` and no project filter applies.
- **OTB-2 (MUST)**: `modelBuilder.HasOutbox()` (public extension in `OutboxModelBuilderExtensions`) applies one shared `IEntityTypeConfiguration<OutboxEvent>`: table `outbox` in the context's default schema (the module schema `UseOrvanoConventions` set), the columns in _Outbox table_ below, `ck_outbox_type` (`char_length(type) BETWEEN 3 AND 100`), `ck_outbox_trace_parent` (`char_length(trace_parent) <= 55`), the partial index `ix_outbox_pending` on `(id)` where `dispatched_at IS NULL` (EF `HasFilter`, spec 0011 COL-7), and the storage parameter `autovacuum_vacuum_scale_factor = 0.05` (each row is inserted, updated once, and deleted after 7 days). A module that announces events calls it in `OnModelCreating` and generates its next migration, which creates `<module>.outbox`. The type pattern and payload size are checked in code (OBX-1, PUB-1), not in SQL.
- **OTB-3 (MUST)**: `trace_parent` is new to spec 0007 EVT-1's column list: the W3C `traceparent` of the publishing activity, carried to every delivery job so a subscriber's trace links back to the request that published (JTL-3).

**Publish (PUB)**

- **PUB-1 (MUST)**: `Outbox` (internal, Infrastructure, registered by `AddInfrastructure` for every command) checks everything before it changes anything (PUB-2), then: now from `TimeProvider`; the payload serialized with the event's `JsonTypeInfo`; `context.Add(new OutboxEvent { Id = Guid.CreateVersion7(now), Type = TEvent.Type, Payload, ProjectId = projectId, OccurredAt = now, TraceParent = <Activity.Current.Id when W3C> })`; enlist `SignalKind.Job` with no values on the same context through `SignalBus` (spec 0007 EVT-3: the dispatcher wakes on the `job` signal; SND-4 makes it one signal per transaction); add an on committed action (SND-1) that counts `outbox.published` (OTL-1); and add the PUB-3 check. It returns the id. The row joins the transaction because the caller saves it in that transaction, so it commits or rolls back with the change, and an execution strategy retry (SND-6, which clears the change tracker) adds it again in the new attempt only.
- **PUB-2 (MUST)**: Checks, in this order, each before any change: the event type is registered (`IOutboxRegistry.FindEvent(TEvent.Type)` with CLR type `TEvent`, else `InvalidOperationException` "No outbox registers the event type '<type>'. Add it with services.AddOutbox (spec 0013 OBX-3)."); `projectId` is not `Guid.Empty` and the serialized payload is at most 64,000 UTF-8 bytes (each else `ArgumentException`; the limit leaves room for DLV-2's envelope under ENQ-3's 65,536); `TransactionSignals.EnsureEnlistable(context)` (ENQ-2: an open transaction, a platform database context, not joined, with SND-5's messages); the context's schema (`OrvanoConventions.SchemaOf`) equals the type's first segment (else `InvalidOperationException` "Publish <type> on the <schema> module's own DbContext (spec 0013 PUB-2)."), so a module publishes only its own events into its own outbox; and the context's model maps `OutboxEvent` (else `InvalidOperationException` "The <schema> context has no outbox table. Call modelBuilder.HasOutbox() in OnModelCreating (spec 0013 OTB-2).").
- **PUB-3 (MUST)**: An event that is added but never saved must not vanish while its `job` signal goes out. `TransactionSignals` gains `AddBeforeCommit(DbContext context, object key, Action<DbContext> check)`: at most one check per key per transaction, kept in `PendingSignals` and cleared with the batch (SND-3), run by `SignalTransactionInterceptor.TransactionCommittingAsync` in add order before any `pg_notify`. `Outbox` adds one check per transaction (key: the `Outbox` type): any `OutboxEvent` entry still in state `Added` throws `InvalidOperationException` ("An event published through IOutbox was not saved. Call SaveChangesAsync before the commit (spec 0013 PUB-3)."), which fails the commit, so `InTransactionAsync` rolls back and nothing is sent. The synchronous `Commit` already refuses a transaction with a `job` enlist (SND-8).
- **PUB-4 (MUST)**: The intended call, inside `InTransactionAsync` (SND-6), with the change and the event in one `SaveChangesAsync`:

  ```csharp
  await db.InTransactionAsync(async token =>
  {
      db.Users.Add(user);
      outbox.Publish(db, new UserCreatedV1(user.Id), projectId: null);
      await db.SaveChangesAsync(token);
  }, cancellationToken);
  ```

**Dispatcher (DSP, `Orvano.Infrastructure/Outbox/`)**

- **DSP-1 (MUST)**: `OutboxDispatcher` (internal `BackgroundService`) is registered by `AddJobRunner` (JOP-3), so only `serve` with the `worker` role runs it. It subscribes to `WorkerWake` in its constructor (WAK-5) and runs one pass (DSP-2) at start and one after every wake: the `job` signal, the poll tick (it ignores the poll flag, `Take()`), a signal reconnect, and a full claim. It adds no listener code, timer, or observer of its own; the always on poll is its fallback for a lost signal.
- **DSP-2 (MUST)**: A pass goes round the registered outboxes (`IOutboxRegistry.Outboxes`, schema order), one batch (DSP-3) per outbox per round, and starts another round with only the outboxes whose last batch was full (100 rows), until none is. So one busy outbox cannot hold the others back by more than one batch. With no outbox registered a pass does nothing and sends no query.
- **DSP-3 (MUST)**: A batch is one `InTransactionAsync` (read committed) on a `JobsDbContext` from a new async scope, so its row locks, the jobs it enqueues, and the dispatched mark commit or roll back together (spec 0007 EVT-3). Inside, in order:
  1. `SELECT id, type, payload::text AS payload, project_id, occurred_at, trace_parent FROM "<schema>".outbox WHERE dispatched_at IS NULL ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED` (through `ix_outbox_pending`). Rows another dispatcher holds, and rows of transactions not yet committed, are skipped.
  2. For each row in `id` order, for each of `IOutboxRegistry.SubscribersOf(type)` in name order, one delivery job through `JobQueue.InsertAsync` on the same context (ENQ-1, DLV-1 to DLV-3). Every inserted due job enlists `job` (ENQ-4), so the commit wakes the runners once.
  3. `UPDATE "<schema>".outbox SET dispatched_at = @now WHERE id = ANY(@ids)` for every selected row, with or without subscribers.
  4. On committed actions count `outbox.dispatched` and record `outbox.lag` (OTL-1).
- **DSP-4 (MUST)**: A row whose type no outbox registers (a rollback to an older version, or a type removed from code) gets no job, is marked dispatched like the rest, logs a Warning with the outbox and type, and is counted with type `unknown`. A registered type with no subscribers is the normal case and logs nothing above Debug.
- **DSP-5 (MUST)**: Each batch runs with a token linked to the stopping token and `OutboxDispatcher.BatchBound` (10 s, a `CancellationTokenSource(BatchBound, timeProvider)`, spec 0002 ASY-7), so a stalled database cannot hold the loop. A batch that throws or is cut off rolls back whole: nothing is enqueued and nothing is marked, so no event is lost. It is logged at Error (not at all when the host is stopping), that outbox sits out the rest of the pass, and the next wake (at most `PollInterval`) tries again. The loop never ends while the host runs (WAK-4's rule).
- **DSP-6 (MUST)**: Shutdown: the loop stops waiting for wakes, and a batch in flight is cancelled by the stopping token and rolls back. Nothing has to be released: the dispatcher holds no lease, and its locks end with its transaction. A commit whose outcome is unknown either happened or did not; in both cases the next pass is correct, because a second dispatch of the same row finds every delivery's dedupe key taken (DLV-4).
- **DSP-7 (MUST)**: Every pass runs the queries even when nothing waits, so each wake costs one indexed query per registered outbox. The dispatcher's own commit sends a `job` signal that wakes every `WorkerWake` subscriber, the dispatchers included, so a dispatch is followed by one empty pass on each worker. Both are accepted: they are cheap, and a separate `outbox` signal kind would change BUS-1 and the listener for a saving the always on poll does not need.
- **DSP-8 (MUST)**: The schema is the one identifier in this section's SQL that is not fixed text. `OutboxSql` (internal) builds each outbox's statements once, from a schema `AddOutbox` already checked against `^[a-z][a-z0-9_]{1,30}$` (OBX-3), quoted with `"`, through `FormattableStringFactory.Create`, and runs them with `SqlQuery` and `ExecuteSqlAsync`, so every value stays a parameter (spec 0002 DAT-6, amended to allow exactly this: a code registered, pattern checked identifier, never a value). Each call site carries `// Deviation DAT-6: identifier from a registered outbox schema (spec 0013 DSP-8)`. `ExecuteSqlRaw` and `FromSqlRaw` stay banned.

**Delivery (DLV)**

- **DLV-1 (MUST)**: Each subscriber is its own job kind, named by its subscriber name (OBX-5), with its own `JobKindOptions` (defaults: lease 5 minutes, 10 attempts, timeout 1 hour). Its `JobRegistration` (built by `AddEventHandler` through the internal constructor, so JQ-5's delegates need no reflection) has job type `OutboxDelivery`, deserializes the envelope (DLV-2), and runs DLV-5. `JobRegistry` sees it like any other kind: its duplicate check, the claim's per kind lease, and the per kind metrics all apply. `JobRegistry.For<TJob>()` is never called for it; only the dispatcher enqueues deliveries, through `JobQueue.InsertAsync` with the registration.
- **DLV-2 (MUST)**: The delivery job's payload is the envelope `OutboxDelivery` (internal sealed record: `Guid EventId`, `string Type`, `DateTimeOffset OccurredAt`, `JsonElement Data`), serialized by SharedKernel's source generated `OutboxJsonContext` with camelCase names: `{"eventId":…,"type":…,"occurredAt":…,"data":{…}}`, where `data` is the outbox row's payload. The delivery copies the event, so it never reads the outbox row and outlives its 7 day retention (a dead delivery that feature 46 retries later still has its event). PUB-2's 64,000 byte limit keeps the envelope under ENQ-3's 65,536; a unit test pins the envelope overhead for a 100 character type.
- **DLV-3 (MUST)**: Each delivery is inserted with `ProjectId` = the row's `project_id`, `DedupeKey` = `<event id>:<subscriber name>` (the id in `D` format, at most 137 characters, within ENQ-3's 200), `RunAt` = now, and `trace_parent` = the row's `trace_parent`. `JobQueue.InsertAsync` gains an internal `traceParent` argument for this; ENQ-1's callers pass `Activity.Current`'s as before.
- **DLV-4 (MUST)**: Dedupe still holds under JDB-2's scope: the key is unique per `(kind, project_id, dedupe_key)`, the kind is the subscriber, and the project is the row's own, which never changes, so a second dispatch of the same event to the same subscriber always collides and returns `null`. The window is safe: an event is dispatched again only when a dispatch commit's outcome was unknown, at the next pass, and the delivery's dedupe key is held until the job row is deleted (7 days after success, 30 after death, SCH-7). Two subscribers of one event, or one subscriber of two events, never collide.
- **DLV-5 (MUST)**: Running a delivery: the runner's scope is set up as for any job (CLM-7: `Caller.System` and the row's project); the run delegate reads `data` with the event's `JsonTypeInfo` from `IOutboxRegistry.FindEvent(Type)`, builds `EventContext` from the envelope and the `JobContext`, and calls the scoped `IEventHandler<TEvent>`. A type no longer registered, or `data` that does not deserialize, throws and is a failed attempt (OUT-2), so a rollback to an older version can drain it before it dies. Outcomes, retries, backoff, dead marking, timeouts, and shutdown release are the job queue's (OUT-1 to OUT-8); `PermanentJobFailureException` works in an event handler too.
- **DLV-6 (MUST)**: Delivery is at least once and unordered (spec 0007 EVT-3): a subscriber that needs order compares `EventContext.EventId` (uuid v7, time ordered) or `OccurredAt` with what it stored. The outbox gives no exactly once and no per subscriber cursor.

**Cleanup (OCL)**

- **OCL-1 (MUST)**: The built in `outbox.cleanup` schedule (cron `37 3 * * *`, 20 minutes after `jobs.cleanup`, kind `outbox.cleanup`, payload `{}`) and its handler, registered by `AddInfrastructure` with default kind options except `MaxAttempts` 3, its JSON type info from `InfrastructureJsonContext` (SCH-7's pattern). For each registered outbox it repeats `DELETE FROM "<schema>".outbox WHERE id IN (SELECT id FROM "<schema>".outbox WHERE id < @boundary AND dispatched_at IS NOT NULL ORDER BY id LIMIT 5000)` (DSP-8's identifier rule) until it deletes fewer than 5000, each statement in its own `InTransactionAsync` on `JobsDbContext`. Retention and chunk are constants (spec 0007 EVT-3).
- **OCL-2 (MUST)**: `@boundary` is `OutboxIds.Floor(now − 7 days)`: the smallest uuid v7 of that millisecond (its timestamp bits, version 7, the RFC variant, every random bit zero), a pure internal function unit tested at its bounds. Because PUB-1 makes each id from `occurred_at`, `id < @boundary` means "occurred more than 7 days ago", and the scan walks the primary key instead of needing an index on `dispatched_at`. A row that is still undispatched is never deleted, whatever its age.

**Telemetry (OTL)**

- **OTL-1 (MUST)**: Metrics on `InfrastructureTelemetry`: `orvano.infrastructure.outbox.published` (counter, `{event}`, tag `type`; confirmed commits only, PUB-1); `orvano.infrastructure.outbox.dispatched` (counter, `{event}`, tag `type`, `unknown` for a type no outbox registers, DSP-4; confirmed commits only); `orvano.infrastructure.outbox.lag` (histogram, `s`, tag `outbox` (the schema), commit time of the dispatch minus `occurred_at`, with JTL-1's bucket boundaries). Deliveries need no metric of their own: they are `jobs.enqueued`, `jobs.attempts`, and `jobs.duration` tagged with the subscriber's kind. Type and schema tags come from registrations, never from the row's text; no event, project, or user id tags.
- **OTL-2 (MUST)**: Logs on `InfrastructureLog`, event ids `LogEventIds.Infrastructure + 200` to `+ 299`: dispatcher started (Information: outbox count, subscriber count); batch dispatched (Debug: outbox, events, jobs); batch failed (Error: outbox, exception); unknown type (Warning: outbox, type); event published (Debug: type, id, payload); cleanup (Information: outbox, deleted count). Payloads only at Debug (spec 0006 LOG-2).
- **OTL-3 (MUST)**: Each batch that selects at least one row runs in an activity `outbox dispatch <schema>` (kind `Internal`) on the `Orvano.Infrastructure` source, tagged `orvano.outbox.schema` and `orvano.outbox.events`. Each delivery attempt is a job attempt (JTL-3), linked to the publishing trace through the copied `trace_parent` (DLV-3).

**Guard rails (OGR)**

- **OGR-1 (MUST)**: Modules may: register their own outbox and events (OBX-3), publish their own events on their own context inside a transaction (PUB-2), subscribe to any module's events through `Contracts` (OBX-5), and read `IOutboxRegistry`. Modules may not: write, read, or delete any outbox row except through `Publish` (their own included), publish another module's event type (PUB-2 refuses it), or run the dispatcher or deliveries themselves.
- **OGR-2 (MUST)**: Enforcement: `BannedSymbols.Modules.txt` adds `T:Orvano.SharedKernel.Outbox.OutboxEvent` (OGR-1: publish through IOutbox), so a module cannot `Add`, query, or delete the entity; `HasOutbox()` names it only inside SharedKernel, and generated migrations name it as a string. The CAC-5 module source scan also fails on the case sensitive pattern `\b[a-z][a-z0-9_]*\.outbox\b` (raw SQL naming a schema's outbox; the C# namespace `Orvano.SharedKernel.Outbox` does not match). The reflection test checks the new ban like the others.
- **OGR-3 (MUST)**: A test in `Orvano.Host.IntegrationTests` checks, for every outbox the host registers, that a `DbContext` in `MigrationOrder` has that schema and maps `OutboxEvent`, so a module cannot register an outbox whose table no migration creates. PUB-2's model check catches the same mistake at the first publish.

**Pool (amends JOP-2 and JOP-4)**

- **OPL-1 (MUST)**: The dispatcher's loop uses one platform connection, serially, like the runner's loop (JOP-4), and its batch takes no second one (the inserts run on the batch's own context). So a worker process has two loop connections, and JOP-2's limit becomes `PoolSize` / 2 − 2, with `DatabaseOptions.PoolSize` at least 6 so the limit stays at least 1. Steady state: `Concurrency` + 2 ≤ `PoolSize` / 2; worst case (every handler and every renewal at once): 2 × `Concurrency` + 2 ≤ `PoolSize` − 2. At the default pool of 30 the default concurrency is at most 13. JOP-2, JOP-4, AC-26, and spec 0007 JOB-4 are amended to match.

**Testing time (OTS)**

- **OTS-1 (MUST)**: Every time in this section comes from the injected `TimeProvider`: `occurred_at` and the id at publish, `dispatched_at`, the lag, and the cleanup boundary are SQL parameters, and no statement calls `now()`, `clock_timestamp()`, or `CURRENT_TIMESTAMP` (JTS-1's source scan covers `Orvano.Infrastructure/Outbox/`).
- **OTS-2 (MUST)**: `JobsDriver.RunDueAsync` (JTS-2) dispatches too: after the schedule tick, each pass runs a full dispatch (DSP-2) and then claims and runs due jobs, and it repeats until a dispatch moves nothing and a claim returns nothing, so a handler that publishes an event that another subscriber handles completes in one call. The 1000 attempt cap stays. `JobsDriver.DispatchAsync(IServiceProvider, CancellationToken)` runs one full dispatch alone and returns the count of events it marked, for tests that check the outbox without running handlers. Both work on any role. A module test publishes in `InTransactionAsync`, advances `ManualClock` when it needs to, and calls `RunDueAsync`.
- **OTS-3 (MUST)**: The tests prove the path with a test only platform context in `Orvano.Testing` (`SampleOutboxDbContext`, schema `sample`, an entity and `HasOutbox()`, registered with `AddOutbox("sample", …)`, its tables created from its model by the test fixture), so this milestone needs no module to own an outbox yet.

### Outbox state transitions

Event row: `pending` (`dispatched_at` null, inserted by the publishing commit) → `dispatched` (DSP-3, in the same commit as its deliveries) → deleted (OCL-1, 7 days after `occurred_at`). A rolled back publish never exists. Delivery: a job of the subscriber's kind, `queued` → … as in _Job state transitions_.

Dispatcher: `Starting` → `Running` (a pass per wake) → `Stopping` (a batch in flight rolls back) → `Stopped`.

### Outbox invariants

- An outbox row exists only if the transaction that published it committed, and a published event that was never saved fails its commit instead of vanishing.
- A row is marked dispatched in the same commit that enqueues its deliveries: never marked without its jobs, never enqueued without being marked.
- Each subscriber gets at most one delivery job per event while that job row lives (dedupe on kind, project, and `<event id>:<subscriber>`), and at least one once a worker runs.
- A module writes only its own outbox, only through `IOutbox`, and only for its own event types.
- Undispatched rows are never deleted; dispatched rows go 7 days after they occurred.
- Every time the outbox stores or compares comes from the app's `TimeProvider`.

### Outbox security model

No caller facing surface. Events hold ids and codes (spec 0011 CLS-2), and `payload` is marked `Personal`, like a job's, so feature 49 and LOG-3 treat it that way; the copy in each delivery job lives 7 or 30 days (SCH-7). Deliveries run as `Caller.System` with the event's project, which only the publishing code chose, so a subscriber acts for the project the event names and no other (JQ-6). A project's own input never chooses a type, a schema, or a subscriber: types and subscribers come from code, and the one identifier in the SQL comes from a registration (DSP-8). Any session with the platform owner role can write outbox rows directly (PG-2a); that role already owns every platform table.

### Outbox configuration required

- None new. The dispatcher uses `ORVANO_JOBS__POLLINTERVAL` (its fallback wake) and counts against `ORVANO_DATABASE__POOLSIZE`, which must now be at least 6 (OPL-1); `ORVANO_JOBS__CONCURRENCY` defaults to at most half the pool less two (13 at the default pool of 30).

### What EVT-4's readers will need

Not built here; named so features 33 to 36 do not add a second event path (spec 0007 EVT-4):

- A subscription to every event type (or every type of one schema), so realtime and webhooks need not list types; today `AddEventHandler` takes one type.
- Event payloads richer than ids and codes for webhook bodies, or a rule that the webhook sender loads the current state by id (preferred: keeps CLS-2 and erasure simple).
- Replay for a late or new webhook endpoint, which the 7 day retention allows only if the reader keeps its own position (the uuid v7 `id` orders events well enough for that).
- Per project fan out limits and a separate concurrency limit for delivery kinds (feature 23's `MaxConcurrency`), so one noisy project cannot fill a worker's slots.

## Consequences

**Positive**:

- Module code for "invalidate everywhere" is one line inside a transaction, and the signal cannot leave before the change or survive a rollback.
- Retries, rollbacks, `ExecuteUpdate`, and several module contexts in one request (spec 0011 TXN-1: each step commits its own context, so each step's signals ride its own commit) need no special handling.
- The writer sees its own change on its next request, and every other instance within milliseconds; a lost signal, or a reader racing the commit, costs at most the entry's expiry (60 seconds for security related entries).
- Modules keep using plain `HybridCache`; the bypass is invisible to them, and an entry with no options still gets the security cap.
- The job runner and feature 14 plug in through two small interfaces and get timing, backoff, and resync for free.

**Negative / tradeoffs**:

- Every write that invalidates a cache must run in an explicit transaction (`InTransactionAsync`), even a single `SaveChanges`. That is one wrapper call per write path, enforced by an exception, not the compiler.
- `work` inside `InTransactionAsync` must be safe to run twice, because a commit with an unknown outcome is retried. That is DAT-8's existing risk, now stated.
- Signals must be enlisted on the context that began the transaction; a context that joined it with `UseTransaction` gets an exception, and committing through a joined context is unsupported.
- A slow handler is cut off after 10 seconds, so an observer's fallback poll on a struggling database can be abandoned and wait for the next tick; a loop lagging past the heartbeat timeout turns caching off until it catches up.
- A connection that keeps dropping within its first 30 seconds backs off up to `ReconnectBackoffCap` before each retry, so recovery after a brief flap can take up to that long.
- Every boot runs each observer's disconnect hook and one fallback poll just before the first connect, an extra database read per observer per start.
- While disconnected, and in commands without a listener, every cached read hits the database; a long outage of the signal connection (but not of the database) raises platform database load.
- The writer applies its own tags twice (on commit and on the echo). Cheap, but visible in metrics.
- Handlers share one loop; a slow one delays the rest (HND-4).
- Jobs run at least once, never exactly once: every handler must be idempotent, and a commit or outcome write with an unknown result costs an extra run or a lost attempt (CLM-3, OUT-7).
- Enqueue inside a transaction is one SQL round trip at call time, not deferred to `SaveChanges`, and a dedupe key held by another open transaction makes the insert wait for that transaction.
- A delayed job or a retry starts up to `PollInterval` (5 s) after it is due; only due now jobs get a signal.
- Lease expiry trusts the replicas' clocks to agree within seconds (CLM-8).
- A crashed worker's jobs wait for their lease (5 minutes by default) before another worker picks them up, and a lease lost to a renewal that did commit costs an attempt the same way.
- A handler that ignores its token after a timeout keeps its slot until the process restarts; the job's retry may meanwhile run on another worker, so idempotence still matters.
- `CancelProjectJobsAsync` reaches a running handler only at its next renewal (up to lease ÷ 3), and does not by itself stop jobs a racing transaction enqueues (AC-30).
- Every transaction that sends `pg_notify` takes PostgreSQL's commit time notify lock (general PostgreSQL behavior, not measured here), so the `job` signal bounds enqueue throughput; the always on poll means signals could later be coalesced or dropped without a correctness change.
- Claims and outcomes are not HOT updates, since `status` is in the index predicates (JDB-2).
- An unregistered kind or unreadable payload burns its attempts (about 6 hours with the backoff) before it dies, instead of dying at once.
- Schedules live in code, and `jobs.schedule` keeps only their state: changing a cron, kind, or payload is a release, an operator can only toggle `enabled` (feature 46), and the table alone does not say what a schedule runs.
- `Concurrency` defaults to at most half the platform pool less two, so a large machine with the default pool of 30 runs 13 jobs at once, not 16 (spec 0007 JOB-4 amended twice; milestone 3 took one more for the outbox dispatcher's loop, OPL-1); in exchange the workers can never take the whole pool (JOP-4), and a pool below 6 no longer starts.
- A dedupe key no longer spans kinds or projects, so a caller that wanted one key to block jobs of two kinds cannot; no planned caller does (schedules, EVT-3, and the feature 13 teardown key their own kind).
- An expired lease on its last attempt is marked `dead` up to `PollInterval` later than before; nothing can run it meanwhile (CLM-1).
- Events reach subscribers at least once and in no set order, so every event handler is idempotent and compares event ids or times when order matters (DLV-6).
- A published event must be saved before the commit; forgetting `SaveChangesAsync` is caught by a before commit check that fails the commit, not by the compiler (PUB-3).
- Each delivery copies the event into a job row, so an event with five subscribers is stored six times until cleanup; payloads are ids and codes, so this stays small (DLV-2).
- Each subscriber is its own job kind, so a subscriber name is a stable identity: renaming one is a new subscriber, and events already delivered to the old name are not delivered again under the new one (OBX-5).
- Every worker wake runs one indexed query per registered outbox, and each dispatch is followed by one empty pass on every worker, because the dispatcher's own commit sends a `job` signal (DSP-7).
- The dispatcher's loop takes one more platform connection per worker, so the default concurrency at pool 30 drops to 13 and a pool below 6 no longer starts (OPL-1).
- One identifier (the outbox schema) is spliced into SQL text, a narrow deviation from DAT-6 that the pattern check and quoting keep safe (DSP-8).
- An event of a type removed from code is marked dispatched and dropped with a Warning, so a rollback to an older version loses events that only the newer version had subscribers for (DSP-4).

**Neutral**:

- Spec 0007 gains a `["*"]` meaning for `session`, `SignalOptions` in REP-2's list, and five `ORVANO_SIGNALS__*` variables.
- Modules lose direct `NpgsqlDataSource` connections; none use them today, and spec 0007 PG-3 already routes project connections through `IProjectDbConnectionFactory`.
- Feature 14's label writes (spec 0012 LBL-3) and every EVL-5 grant change call `Invalidate` inside `InTransactionAsync`.
- Milestone 2 adds `Cronos` (MIT, already named in spec 0007 REP-2), the first `DbContext` and migration in the repo (`jobs`), and two `ORVANO_JOBS__*` variables; spec 0012 PRJ-3 gains `JobAccessScope` as the one setter outside the access layer.
- A new package, `Microsoft.Extensions.Caching.Hybrid` (MIT, on spec 0009 DEP-1's list), and a new modules only banned symbols file.
- Milestone 3 adds no package, no variable, and no table of its own: each module that announces events adds `<module>.outbox` through its own migration, and the first is feature 13's or 14's. Spec 0007 EVT-1 to EVT-3 and JOB-4 and spec 0002 DAT-6 point to this section.
