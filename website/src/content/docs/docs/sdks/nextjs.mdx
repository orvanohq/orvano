`@orvano/nextjs` connects a Next.js App Router app (Next.js 15 or later) to Orvano. It builds on [`@orvano/js`](/docs/sdks/js/) and keeps the user's session in two cookies, so server components, server actions, route handlers, and the browser all see the same signed in user.

## Install

<Code code={`npm install @orvano/nextjs@${version}`} lang="sh" />

The [Next.js quickstart](/docs/quickstarts/nextjs/) builds a full app with it. This page explains the parts.

## The session cookies

| Cookie | Holds | Readable by script |
|---|---|---|
| `orvano_access` | the access token, until it expires (15 minutes) | yes, so client components can call Orvano |
| `orvano_refresh` | the refresh token, until the session ends | no, it's `HttpOnly` |

Both are `SameSite=Lax`, `Path=/`, and `Secure` everywhere except on `http://localhost`.

## On the server: `createServerClient`

Make one client per request, never a shared one:

```ts
import { createServerClient } from '@orvano/nextjs'
import { cookies, headers } from 'next/headers'

export async function orvano() {
  return createServerClient({
    endpoint: process.env.NEXT_PUBLIC_ORVANO_ENDPOINT!,
    project: process.env.NEXT_PUBLIC_ORVANO_PROJECT!,
    cookies: await cookies(),
    requestHeaders: await headers(),
  })
}
```

It reads the session from the cookies. In a server action or a route handler it also writes them, so sign the user in there: `account.create` and `account.createPasswordSession` set both cookies, and `account.deleteCurrentSession` clears them. Server components can't set cookies, so there the session is read only.

`requestHeaders` passes the browser's IP address and user agent on to Orvano, so the user's [session list](/docs/auth/manage-sessions/) shows their browser rather than your Next.js server.

The server client is a client SDK: it acts as the signed in user and has no API key. To manage users from your Next.js server, also make an [`@orvano/js/server`](/docs/sdks/js/#on-your-server) client with an API key.

## Keep the session fresh: `updateSession`

Call `updateSession` from `proxy.ts` (`middleware.ts` before Next.js 16). It refreshes the session when the access token has less than a minute left, and clears both cookies when the session has ended:

```ts title="proxy.ts"
import { updateSession } from '@orvano/nextjs/server'
import type { NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  return updateSession(request, {
    endpoint: process.env.NEXT_PUBLIC_ORVANO_ENDPOINT!,
    project: process.env.NEXT_PUBLIC_ORVANO_PROJECT!,
  })
}

export const config = {
  matcher: ['/((?!_next/static|_next/image|favicon.ico).*)'],
}
```

## In the browser: `createBrowserClient` and the route handler

Client components use `createBrowserClient`. It reads the access token from the `orvano_access` cookie, and it never sees the refresh token: it asks your app's own route handler to refresh, sign out, finish an emailed link, sign in with an emailed code, or sign in with a provider. Mount that handler once:

```ts title="app/api/orvano/[...orvano]/route.ts"
import { createOrvanoRouteHandler } from '@orvano/nextjs/server'

export const { GET, POST } = createOrvanoRouteHandler({
  endpoint: process.env.NEXT_PUBLIC_ORVANO_ENDPOINT!,
  project: process.env.NEXT_PUBLIC_ORVANO_PROJECT!,
})
```

```tsx
'use client'
import { createBrowserClient } from '@orvano/nextjs'

const orvano = createBrowserClient({
  endpoint: process.env.NEXT_PUBLIC_ORVANO_ENDPOINT!,
  project: process.env.NEXT_PUBLIC_ORVANO_PROJECT!,
})
```

The handler answers `POST` requests only from your app's own origin: the request's `X-Forwarded-Host` (else its `Host`) and scheme. Behind your own proxy (Caddy, nginx, a tunnel), pass the browser's host through, either as `Host` or as `X-Forwarded-Host`, and set `X-Forwarded-Proto` when the proxy ends TLS; Caddy and Vercel do both by default. The same origin builds the provider callback URL. Its one `GET` action, `.../oauth-callback`, is where a provider sends the browser back after [provider sign in](/docs/auth/sign-in-with-google/); a cookie only that browser holds binds it, so nobody else can finish the sign in. No action finishes an emailed link on `GET`, so a mail scanner that opens a link can't use it up.

Sign users in from a server action rather than the browser: a session started in the browser keeps only the access token, so it lasts 15 minutes.

The handler's `POST` actions, under its path (`/api/orvano` by default):

| Action | What it does |
|---|---|
| `refresh`, `signout` | Trades the refresh cookie for a new pair; ends the session and clears both cookies |
| `redeem`, `email-code` | Finishes an emailed link, or signs in with an emailed code, and sets the cookies |
| `oauth` (and `GET oauth-callback`) | Starts and finishes a provider sign in or link |
| `sign-up` | Signs up and sets the cookies; while the project requires verified emails or MFA it sets none and answers `{ verificationRequired: true }` |
| `anonymous`, `anonymous-upgrade` | Signs a [guest](/docs/auth/anonymous-users/) in; makes the signed in guest permanent and refreshes the cookies, or answers `{ verificationRequired: true }` while the upgrade waits for its emailed link |
| `mfa`, `totp-confirm`, `mfa-verify`, `mfa-passkey`, `passkey-challenge`, `passkey` | The second step, turning MFA on, step up, and passkey sign in |
| `mfa-enroll-totp`, `mfa-enroll-totp-confirm`, `mfa-enroll-passkey`, `mfa-enroll-passkey-confirm` | The first factor a project that [requires MFA](/docs/auth/mfa/#require-mfa-for-every-user) asks for, with the ticket in the `orvano_mfa` cookie |

## The visitor's address

Every call from your Next.js server tells Orvano which visitor it is for, in the `X-Orvano-Client-IP` header, so sessions show the user's address and rate limits count each user rather than your server. By default the address comes from `x-real-ip`, else the rightmost `x-forwarded-for` value. When your host sets another header, pass `clientIp` to `createServerClient`, `createMiddlewareClient`, `updateSession`, and `createOrvanoRouteHandler`, and list your server on the **App servers** card of the project's [Security](/docs/console/security/) page. [Rate limits](/docs/concepts/rate-limits/#from-nextjs) has the header for each host.

## Emailed links and codes

The page an emailed link lands on is a client component with a **Continue** button that calls `orvano.client.redeemLink()`. A password reset link needs the new password: `redeemLink(undefined, { password })`. An emailed code signs in with `orvano.client.signInWithEmailCode(email, code)`. Send the emails themselves from a server action with `createServerClient`. Each [auth guide](/docs/auth/email-verification/) has the Next.js version of its flow.

### MFA and passkeys

A sign in that needs the [second step](/docs/auth/mfa/) keeps its ticket in the `orvano_mfa` cookie (`HttpOnly`, 5 minutes), never in a response: a server action gets `result.mfa` with an empty `ticket` and the `factors`, and a provider sign in redirects to `mfaPath` (default `/sign-in/mfa`), an option of `createOrvanoRouteHandler`. On that page, `orvano.client.completeMfa({ totpCode })` posts the factor to the route handler, which sets the session cookies. `confirmTotp`, `verifyMfa`, `signInWithPasskey`, and a passkey answer go through the handler too, so the refresh token never reaches the browser. [Passkeys](/docs/auth/passkeys/) has the rest.

## Errors

Refused calls throw `OrvanoError`, re-exported from this package with `ErrorCode`. See [Errors](/docs/concepts/errors/).
